# CmdBox 技术选型

> 来源：网页版 ChatGPT 对话“命令执行工具设计”（会话 ID：6a8970d8-9918-83e8-93f6-c194c8df47ea）。
> 保存方式：以下正文按当前会话读取接口返回内容原样保存，不对原讨论进行压缩或重写。

---

我会直接定：**Tauri 2 + React + TypeScript + Rust + SQLite**。

这个组合和 CmdBox 的需求非常匹配，而且我建议**Windows 先做，但架构从第一天保持 macOS/Linux 可扩展**。

### 为什么选 Tauri，而不是 Electron

CmdBox 本质上不是一个内容型桌面 App，而是一个**高权限本地工具**：

```text
选择本地文件夹
↓
拼装命令
↓
启动 PowerShell / CMD / Bash
↓
读取 stdout / stderr
↓
终止进程
↓
保存执行记录
```

Tauri 2 本身就是 Web UI + Rust Native Core 的架构，而且官方已经提供文件/文件夹选择、Shell、SQL 等桌面能力。它的文件选择器原生支持 `directory: true` 和 `multiple: true`，正好对应我们前面定义的 `Folder` / `Folder[]` 参数。citeturn955875search0turn955875search2

Electron 当然也完全能做，Node/Electron 的进程模型对 stdout、PID、kill、cwd、env 等支持都很成熟。citeturn138412search0turn138412search3 但对于 CmdBox，我更希望形成这种边界：

```text
┌─────────────────────────────────────┐
│             React UI                │
│                                     │
│ 表单 / 搜索 / Command Block / 日志  │
└──────────────────┬──────────────────┘
                   │ Typed IPC
                   ↓
┌─────────────────────────────────────┐
│             Rust Core               │
│                                     │
│ Template Engine                     │
│ Command Executor                    │
│ Shell Adapter                       │
│ Safety Guard                        │
│ Process Manager                     │
│ SQLite Repository                   │
└──────────────────┬──────────────────┘
                   │
          ┌────────┴─────────┐
          ↓                  ↓
    powershell.exe        cmd.exe
    pwsh / bash / zsh
```

而不是：

```text
React
  ↓
直接 child_process
  ↓
系统 Shell
```

CmdBox 是执行破坏性命令的工具，这个区别我认为值得。

# 1. 一个比较重要的决定：不用 Tauri Shell Plugin 作为核心执行器

Tauri 官方 Shell Plugin 确实已经支持 command execute、spawn 和 kill，并且通过 capability/permission 控制权限。citeturn138412search7

但是我**不建议 CmdBox 的核心执行直接写成：**

```ts
Command.create(...)
```

然后前端任意启动进程。

原因在于 CmdBox 天生就需要：

> 用户可以创建任意 Command Block。

这样 Shell Plugin 的命令白名单机制和我们的产品模式并不完全契合。

我更倾向：

```text
React
 ↓
invoke("run_command", {
    commandBlockId,
    params
})
 ↓
Rust
```

Rust Backend 完成：

```text
读取 Command Block
↓
验证参数
↓
安全转义
↓
危险路径检测
↓
生成最终命令
↓
创建进程
↓
监听 stdout/stderr
↓
发送 Event 给 React
```

因此前端没有这样的 API：

```text
executeAnything("xxx")
```

而只有：

```text
runCommandBlock(...)
stopExecution(...)
```

职责会干净很多。

# 2. Command Executor 单独抽象

Rust 后端第一版我就会定义：

```rust
trait ShellRunner {
    async fn execute(
        &self,
        command: &str,
        cwd: Option<&Path>,
        env: &HashMap<String, String>,
    ) -> Result<ExecutionHandle>;

    async fn kill(
        &self,
        execution_id: ExecutionId,
    ) -> Result<()>;
}
```

下面分别实现：

```text
PowerShellRunner
CmdRunner
BashRunner
ZshRunner
```

例如 Windows：

```text
PowerShellRunner

pwsh.exe
    ↓
不存在
    ↓
powershell.exe
```

CMD：

```text
%COMSPEC%
```

macOS：

```text
/bin/zsh
/bin/bash
```

以后要增加：

```text
FishRunner
PythonRunner
WSLRunner
```

不会改 UI 层。

# 3. stdout / stderr 用事件流，不等命令执行完

绝对不要：

```text
点击执行
↓
loading……
↓
命令全部结束
↓
一次性返回 output
```

比如删除几百万个文件，可能运行很久。

应该：

```text
Rust Process
     │
     ├── stdout ──→ execution://stdout
     │
     ├── stderr ──→ execution://stderr
     │
     └── exit ────→ execution://finished
```

React：

```text
运行中 · 00:42

正在删除……
……
……

[终止任务]
```

这样虽然我们不做 Terminal，但体验还是实时的。

---

# 4. Execution ID

每次运行生成：

```text
execution_id
```

例如：

```text
0198dfaa-...
```

生命周期：

```text
Pending
   ↓
Running
   ↓
Success
```

或者：

```text
Running
   ↓
Failed
```

或者：

```text
Running
   ↓
Cancelled
```

于是 UI 可以可靠地：

```text
stopExecution(executionId)
```

而不是管理 PID。

**PID 不暴露给业务 UI。**

---

# 5. 进程终止要从一开始处理“进程树”

这里很容易踩坑。

假设启动：

```text
CmdBox
  ↓
cmd.exe
  ↓
robocopy.exe
```

如果用户按：

**终止任务**

我们只 kill：

```text
cmd.exe
```

有可能：

```text
robocopy.exe
```

还在跑。

所以 Process Manager 设计目标应该是：

### Windows

管理整个 Process Tree / Job。

### Linux/macOS

管理 Process Group。

最终：

```text
[终止任务]
       ↓
kill execution
       ↓
整个命令树退出
```

而不只是 shell wrapper 退出。

这个需求最好不要后补。

---

# 6. 参数不要在 React 里做字符串替换

这个同样非常重要。

千万不要：

```ts
command.replace("{{path}}", value)
```

例如：

```text
D:\abc & format C:
```

或者 PowerShell：

```text
D:\It's Test
```

很容易出现 shell quoting / injection 问题。

正确架构：

```text
React

{
    paths: [
      "D:\\aaa",
      "D:\\bbb"
    ]
}

        ↓

Rust Template Engine

        ↓

Shell-specific serializer

        ↓

PowerShell

@(
  'D:\aaa'
  'D:\bbb'
)
```

换成 CMD 又是另一套规则。

所以：

> **模板渲染属于 Rust Core，不属于 React。**

# 7. 参数的数据模型

TypeScript 和 Rust 使用同一套概念：

```ts
type ParameterType =
  | "text"
  | "number"
  | "boolean"
  | "select"
  | "file"
  | "folder"
  | "files"
  | "folders";
```

Command Block：

```ts
interface CommandBlock {
  id: string;
  name: string;
  description?: string;

  runner:
    | "powershell"
    | "cmd"
    | "bash"
    | "zsh";

  template: string;

  parameters: ParameterDefinition[];

  workingDirectory?: string;

  destructive: boolean;

  categoryId?: string;

  favorite: boolean;
}
```

这个模型第一版已经够用了。


# 11. 为什么我不优先选 Electron

Electron 最大优势其实非常明确：

```text
React / TypeScript
+
Node
+
child_process
```

一套语言就可以完成整个应用。

而且 Electron 官方进程模型成熟，UtilityProcess 有 PID、stdout 和 kill 等能力。citeturn138412search0turn138412search3

如果目标只是：

> 三天做个内部 demo。

Electron 会很舒服。

但我们现在已经知道 CmdBox 后面会碰：

```text
系统进程
文件系统
Shell quoting
Process Tree
Secrets
权限
系统集成
危险命令检测
```

这时候我宁愿让边界变成：

```text
TypeScript = UI
Rust = 系统
```

而不是整个 App 都运行在 Node + Chromium 的权限模型里。

## 所以我会正式把技术方案定成

```text
                   CmdBox

        ┌────────────────────────┐
        │ React + TypeScript     │
        │ Tailwind + shadcn/ui   │
        │ Zustand + RHF + Zod    │
        └────────────┬───────────┘
                     │
               Tauri IPC/Event
                     │
        ┌────────────▼───────────┐
        │      Rust Core         │
        │                        │
        │ Command Service        │
        │ Template Engine        │
        │ Safety Guard           │
        │ Execution Manager      │
        │ Shell Runners          │
        │ SQLite Repository      │
        └───────┬────────┬───────┘
                │        │
                ↓        ↓
             SQLite   OS Process
                         │
              ┌──────────┼─────────┐
              ↓          ↓         ↓
          PowerShell    CMD     Bash/Zsh
```

**我的选择：Tauri 2。**

Electron 是备选方案，不是首选。

而且接下来我认为我们不要马上写 UI。下一步最值得先定的是 **Command Block Schema + Execution Engine 接口**。这两个东西一旦定下来，前端、数据库和 Rust 后端基本都会顺着它自然展开。
