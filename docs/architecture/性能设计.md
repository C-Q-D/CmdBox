# CmdBox 性能设计

## 文档职责

本文是 CmdBox 当前性能设计的唯一权威文档，约束外部进程输出、IPC、React 渲染、日志、SQLite、文件系统检查和性能验证。本文同时保存已落地的 `CMD-02` 性能事实与后续设计目标；两者必须按下面的状态基线阅读，后续目标不构成当前实现或测试证据。

### 状态基线

| 状态 | 能力 |
|---|---|
| 当前 `CMD-02` | Rust Reader → Aggregator → Batch → 每次 Run 专属 Tauri Channel；32 KiB 或 33 ms Flush；React 最多保留 512 KiB、2048 个非空 Chunk；Run response 前缓存同时受 2048 个事件、2048 个非空 Fragment、512 KiB 约束；当前 Chunk 直接由 React 以纯文本渲染 |
| 后续单元 | 完整持久日志、SQLite Execution Metadata、History、OutputPolicy、虚拟化 Viewer，以及经 Benchmark 决定是否采用约 5 MiB Viewer 容量 |

当前 Rust Core 支持 Windows PowerShell/CMD 和 Text、Number、Boolean、Select、Folder、Folders 六类参数；Preview 返回的 `executionSpecHash` 覆盖完整 Canonical Execution Spec。当前没有 SQLite、History、Outcome、持久日志或虚拟化 Viewer。Output 一律按不可信文本处理，React 通过普通文本节点渲染，不解析 HTML、终端控制序列或可点击链接。

本文标题后缀中的“当前”是仓库已有实现，“后续”是尚未落地的设计，“共同约束”同时约束当前和未来。性能预算若未标为当前硬上限，只是待 Benchmark 校准的工程目标。

总判断：

> **CmdBox 真正需要重点优化的不是模板渲染，也不是 SQLite，而是“外部进程输出 → Rust → IPC → React”这条链路，以及避免 CmdBox 自己干扰用户正在运行的重 I/O 命令。**

尤其你的核心场景是删除几十万/几百万小文件。CmdBox 最不能出现的情况就是：**命令本来 30 秒完成，因为我们疯狂记录日志、刷新 UI、扫描目录，结果变成 60 秒。**

## 一、先明确性能设计目标

我建议从第一天就把 CmdBox 的性能原则定义成：

> **CmdBox 的额外开销应该尽可能接近“直接在终端运行命令”。**

例如用户运行：

```cmd
rmdir /s /q "D:\huge-folder"
```

Terminal 需要：

```text
42.0 秒
```

CmdBox 最理想应该也是：

```text
42.x 秒
```

而不是：

```text
55 秒
```

所以我们需要区分两个性能指标：

```text
External Command Performance
```

和：

```text
CmdBox Overhead
```

前者主要由：

```text
PowerShell
CMD
Robocopy
SSD
NTFS
文件数量
杀毒软件
```

决定。

我们主要控制后者。

# 二、性能风险优先级（设计风险）

我目前会这样排：

| 优先级 | 模块 | 风险 |
|---|---|---|
| 🔴 P0 | stdout/stderr | 高频输出导致 CPU、内存、UI 卡顿 |
| 🔴 P0 | React 日志显示 | 大量文本导致 DOM/React 崩掉 |
| 🔴 P0 | 文件夹处理 | 错误地递归扫描大目录 |
| 🔴 P0 | Log 写盘 | 和删除/复制任务竞争磁盘 I/O |
| 🔴 P0 | IPC | 每行甚至每字符跨 Rust/WebView |
| 🟠 P1 | 内存 | 长任务 Output 无限增长 |
| 🟠 P1 | Template Preview | 参数变化造成重复渲染 |
| 🟠 P1 | SQLite | 高频小事务/错误保存 Output |
| 🟠 P1 | 多任务 | 锁竞争和多重 I/O |
| 🟡 P2 | 搜索 | Command 数量上千后的查询 |
| 🟡 P2 | 启动速度 | 启动时加载过多数据 |
| 🟡 P2 | Command Editor | 大 Template 编辑性能 |

下面分别定。

# 三、第一条铁律：绝对不要扫描目标文件夹（共同约束）

这条和你最开始的痛点直接相关。

比如用户选择：

```text
E:\comp\huge-folder
```

CmdBox **绝对不要为了展示这些东西去扫描目录：**

```text
文件数量：1,832,251
文件夹数量：42,321
大小：87.4 GB
```

因为为了算这些东西，我们自己就得先：

```text
递归遍历整个目录
```

这等于重现 Windows Explorer 删除前预扫描的问题。

因此用户选择文件夹以后，我们只做：

```text
Path Exists?
Is Directory?
Is Root?
Is Dangerous System Path?
```

这些都应该是接近 O(1) 的 metadata/path 操作。

不要做：

```text
calculateFolderSize()
countFiles()
walkDirectory()
scanPermissions()
```

所以快速删除 UI 最好只显示：

```text
3 个文件夹

D:\aaa
D:\bbb
D:\ccc
```

不要显示：

```text
共 2,938,281 个文件
共 124.7 GB
```

除非未来用户主动点击：

> 分析目录

那是另一个独立功能。

这个设计我建议现在就冻结。

# 四、最大的性能热点：stdout / stderr（当前）

假设一个命令每秒输出：

```text
10,000 行
```

如果我们这么做：

```text
Process
 ↓ 每行
Rust
 ↓ 每行 IPC
React
 ↓ setState
DOM
```

这个 App 很快就会卡。

高频 Streaming Data 使用 per-execution Tauri `Channel`，不使用普通全局事件机制。

但只使用 Channel 还不够。

我们需要：

```text
Process stdout
      ↓
   Reader
      ↓
 Output Aggregator
      ↓
   Batch / Chunk
      ↓
 Tauri Channel
      ↓
 React Buffer
      ↓
 Log Viewer
```

而不是：

```text
一行 = 一次 IPC
```

---

# 五、Output 必须 Batch（当前）

比如 Process 连续产生：

```text
aaa
bbb
ccc
ddd
...
```

不要：

```text
IPC 1 → aaa
IPC 2 → bbb
IPC 3 → ccc
IPC 4 → ddd
```

而应该聚合成例如：

```text
32 KiB
```

或者：

```text
最多等待 20~50ms
```

然后：

```text
IPC

aaa
bbb
ccc
ddd
...
```

一次发送。

当前实现策略：

```text
Flush if:

buffer >= 32 KiB
OR
elapsed >= 33ms
```

也就是 UI 最多大约：

```text
30 次更新 / 秒
```

已经足够感觉“实时”。

完全没有必要：

```text
1000 次 / 秒
```

这个参数以后可以根据 Benchmark 调整；当前 Aggregator 已存在并使用上述阈值。

---

# 六、Process Reader 不能被 UI 拖慢（共同约束）

这是一个非常重要的设计。

想象：

```text
robocopy.exe
     ↓
大量 stdout
     ↓
CmdBox UI 卡住
```

如果 Rust 没及时读取 stdout pipe，操作系统 pipe buffer 填满以后，理论上：

```text
robocopy
```

可能被迫等待。

也就是说：

> CmdBox 的日志 UI 反过来把真正的命令拖慢了。

这个是必须避免的。

当前链路是：

```text
Process → Fast Reader → Output Coordinator → Batch → Channel
```

后续 Log Sink 必须从 Drain 后独立分流，不能让写盘或 UI 反向阻塞 Reader。

Fast Reader 的首要职责是：

> **尽快 Drain stdout/stderr。**

UI 是否处理得过来是第二优先级。

极端情况下：

```text
UI 来不及
```

我们宁愿：

```text
少显示部分实时输出
```

也不应该：

```text
阻塞外部 Process
```

因此内部需要：

```text
bounded queue
+
output truncation
```

而不是无限排队。

---

# 七、实时 UI 与完整日志必须分离（当前与后续）

基础数据流：

```text
Rust
 ↓
Channel
 ↓
React
```

后续加入持久日志后再拆成：

```text
                ┌────────→ UI 有界 Chunk Buffer
Process Output ─┤
                └────────→ Persistent Log
```

当前 UI 严格只保留：

```text
最近 512 KiB
+
最多 2048 个非空 Chunk
```

约 5 MiB 或按行数限制是后续虚拟化 Viewer 的候选参数，只能在 Benchmark 后确定，不能描述为当前值。

假设任务总共输出：

```text
800MB
```

React 绝不能持有这 800MB；完整内容只有在后续独立持久日志实现后才可能从日志按段读取。

---

# 八、不要把 Execution Output 放 Zustand（当前）

当前项目没有引入 Zustand；Execution Output 保存在 Command Workspace 的独立局部有界 Buffer 中。以后即使引入 Zustand，也只允许保存低频元数据：

未来 Zustand 可保存：

```text
executionId
status
startedAt
duration
exitCode
progress metadata
```

但是不要保存：

```text
完整 stdout
完整 stderr
```

否则：

```text
output append
↓
Zustand state change
↓
订阅组件 render
↓
大量对象/string allocation
```

很容易形成性能问题。

当前 Output 使用单独的：

```text
ExecutionOutputBuffer
```

当前实现是有字节数与 Chunk 数双上限的数组 Buffer；以后更换数据结构时可以采用：

```text
RingBuffer<OutputChunk>
```

无论内部数据结构如何，它都必须与未来低频业务 Store 分开。

---

# 九、不要不断做大字符串拼接（当前）

尤其不要：

```ts
output = output + newOutput;
```

运行几个小时以后：

```text
512 KiB
+ 5KB
+ 5KB
+ 5KB
...
```

会产生大量字符串复制。

更合理：

```text
[
  chunk1,
  chunk2,
  chunk3,
  ...
]
```

当前通过 Chunk Buffer 管理。

超过限制：

```text
drop oldest chunks
```

最终 UI 看到：

```text
[早期输出已从实时窗口移除]

...
最新输出
```

当前淘汰的早期输出不可恢复；只有后续持久日志落地后，完整历史才可以从 Log 按段读取。

---

# 十、Output Viewer 的当前边界与后续虚拟化

最简单：

```tsx
<pre>{output}</pre>
```

小输出完全没问题。

但几十万行以后会很糟糕。

当前实现直接把最多 512 KiB、2048 个非空 Chunk 映射为有界 `<li><pre>` 列表，React 只生成纯文本节点，不使用 `dangerouslySetInnerHTML`。当前没有虚拟化；有界容量是这一阶段防止 DOM 无限制增长的硬边界。

后续经长输出 Benchmark 证明需要后，ExecutionOutput 可以升级为：

```text
Virtualized Log Viewer
```

只渲染屏幕附近的内容。

例如实际上有：

```text
20,000 行
```

DOM 里可能只有：

```text
100~300 行
```

这样滚动和选择文本才不会随着日志越来越多越来越卡。

后续虚拟化 Output Viewer 应形成独立组件：

```text
ExecutionOutputViewer
```

升级后不要让单个无限增长的 `<Textarea>` 或 `<pre>` 成为架构依赖；这不是当前已实现能力。

# 十一、Log File 也可能拖慢“快速删除”（后续）

这是一个更容易忽略的问题。

假设：

```text
Robocopy
```

正在疯狂读取：

```text
D:\
```

写：

```text
E:\
```

与此同时 CmdBox 又把每一条 stdout 写入：

```text
C:\Users\...\CmdBox\execution.log
```

这其实额外制造了磁盘 I/O。

如果 Output 特别大，就可能对真实任务造成干扰。

所以对于我们自己的内置 Command Block，原则应该是：

> **尽可能让命令本身少输出。**

例如你之前已经用了：

```text
/NP
```

这是对的。

针对内置高性能命令，我们可以进一步尽量避免：

```text
每个文件打印一行
```

而只保留真正有价值的信息。

例如“快速删除多个文件夹”：

```text
正在删除 D:\A
正在删除 D:\B
正在删除 D:\C
```

完全没必要输出：

```text
删除 file001
删除 file002
删除 file003
...
```

这里的性能收益可能比优化 Rust 代码大得多。

# 十二、Output 与 Log 必须设置硬上限（当前与后续）

当前已有的 UI 硬上限是：

```text
512 KiB
+
2048 个非空 Chunk
```

Run response 返回前的临时事件队列还必须同时满足：

```text
最多 2048 个事件
+
最多 2048 个非空 Fragment
+
最多 512 KiB Output 文本
```

后续持久日志落地时再增加：

```text
UI buffer limit

Persistent log limit
```

后续候选值：

```text
虚拟化 UI:
约 5 MiB（待 Benchmark）

单次 Execution Log:
100 MB
```

约 5 MiB 和 100 MB 都不是当前值或最终产品数字，只能在后续 Benchmark 后调整。

关键是：

> **必须存在上限机制。**

当前 UI 达到任一上限后淘汰最旧 Chunk、累计未保留字节，并显示固定的丢弃字节提示。后续持久日志达到独立上限时可以写入固定标记：

```text
[CmdBox: 日志超过限制，后续输出已省略]
```

但 Rust 仍然：

```text
继续 Drain stdout/stderr
```

当前 UI 只停止保留被淘汰的早期 Chunk；后续持久日志达到上限后也只能停止存储，不能停止 Drain。

否则用户随手运行：

```text
某个无限打印日志的脚本
```

几个小时以后 CmdBox 就可能：

```text
磁盘爆满
```

# 十三、Execution OutputPolicy（后续）

内部模型可以提前留出来：

```rust
struct OutputPolicy {
    ui_buffer_bytes: usize,
    persisted_log_bytes: u64,
}
```

暂时不需要在 Command Block Editor 里给用户设置。

它属于：

```text
App-level performance configuration
```

以后如果需要，再扩展：

```text
Normal
Quiet
Verbose
NoCapture
```

不会影响 Execution Engine。

# 十四、Preview 自动刷新与 Debounce（后续）

当前带参数 Command 由用户显式请求 Preview，无参数 Command 每个 Definition generation 自动 Preview 恰好一次，因此没有“每次键入都发 IPC”的当前行为。若后续产品改为参数输入后自动 Preview，流程才是：

```text
用户修改参数
↓
preview_command_block
↓
Rust render
↓
React 显示
```

假设用户输入：

```text
D
D:
D:\
D:\P
D:\Pr
...
```

如果每敲一个字符都：

```text
IPC
DB Query
Parse Template
Render
Hash
IPC
React
```

没必要。

后续自动 Preview 必须：

```text
Input
↓
Debounce 150~250ms
↓
Preview
```

File Picker 改变路径这种离散事件则可以立即 Preview。

# 十五、Template Parse Cache（后续）

当前受限模板支持：

```text
{{value}}

{{#if}}

{{#each}}
```

当前 Preview 和 Run 共享同一 Parser/Renderer 语义，但每次规划都会重新 Parse；后续有性能证据时可以先：

```text
Template String
↓
Parser
↓
AST
```

例如：

```text
[
 Text,
 Variable,
 Text,
 EachNode,
 ...
]
```

然后 Preview 只：

```text
AST
+
Parameters
↓
Renderer
```

而不是每一次：

```text
Parse
+
Render
```

所以内部最好设计：

```text
TemplateCache

key:
commandBlockId + revision
```

例如：

```text
0198xxx:revision-4
```

第一次使用：

```text
parse
```

之后：

```text
reuse AST
```

当 Command Block 更新：

```text
revision 4 → 5
```

Cache 自动失效。

TemplateCache 当前未实现，不能把上述复用 AST 的流程当作 `CMD-02` 事实。

# 十六、大量 Folder 参数与 Artifact（当前与后续）

例如正常：

```text
3 个 folders
```

非常轻。

但理论上用户可以一次拖：

```text
30,000 个文件夹
```

进来。

然后 Template：

```powershell
{{#each paths}}
Remove-Item ...
{{/each}}
```

可能生成数 MB Script。

当前 Rust 会完整构建 Artifact，并只把 Preview 文本截断到 32 KiB；当前尚未实现完整 Artifact 的 8 MB 拒绝上限。后续应该有：

```text
Rendered Script Size Guard
```

比如初始：

```text
8 MB
```

超过以后不允许直接无限渲染。

当前 Runner 输入已经使用 `RenderedExecution`/`ExecutionArtifact::ScriptFile`，不把执行引擎接口写死为任意 Shell 字符串。后续可以继续扩展为：

```text
RenderedExecution
```

而不是写死：

```text
String
```

未来就可以支持：

```text
RenderedExecution
├─ Script
└─ Auxiliary Files
```

例如极端情况下：

```text
30,000 paths
```

可以生成：

```text
paths.json
```

然后 Script 读取路径文件。

Auxiliary Files 当前未实现；架构上不要把：

```rust
fn render() -> String
```

写死成永远只能一个 String。

可以：

```rust
fn render() -> RenderedExecution
```

当前：

```text
RenderedExecution {
    script
}
```

未来扩展不需要改 Execution Engine。

因此当前事实只是 Script File Artifact；大规模参数的额外拒绝上限和 Auxiliary Files 都是后续设计。

# 十七、Preview 有界展示与完整 Execution Spec（当前）

类似问题。

如果用户选择：

```text
10,000 个目录
```

Rendered Script：

```text
2MB
```

然后前端展示：

```text
2MB syntax highlighted code
```

也会非常慢。

当前 Preview Response 是：

```ts
interface PreviewCommandResponse {
  commandBlockId: string;

  revision: number;

  runner: RunnerType;

  parameterSummaries: PreviewParameterSummary[];

  previewText: string;

  fullSizeBytes: number;

  truncated: boolean;

  executionSpecHash: string;

  riskLevel: RiskLevel;

  actionLabel: string;

  safety: PreviewSafetyDecision;
}

interface PreviewParameterSummary {
  parameterKey: string;
  label: string;
  displayValues: string[];
  totalCount: number;
  truncated: boolean;
}
```

比如：

```text
命令预览

Remove-Item 'D:\A' ...
Remove-Item 'D:\B' ...
Remove-Item 'D:\C' ...
...

已省略其余 9,997 项
```

`executionSpecHash` 针对：

```text
完整 Canonical Execution Spec
```

这样：

```text
安全校验
```

和：

```text
UI 性能
```

可以同时保证。

对于 destructive Command，更重要的是单独展示：

```text
目标：10,000 个文件夹
```

而不是要求用户阅读 2MB PowerShell。

`previewText` 当前最多返回 32 KiB，`fullSizeBytes` 表达完整 Artifact 字节数，`truncated` 表达展示是否截断。`parameterSummaries` 同样有界：`totalCount` 表达完整规范化数量，`displayValues` 只返回受控数量并用 `truncated` 标记省略。Safety Warning 也应按稳定类别聚合并设置返回上限，不能把一万个目标转换成一万个 UI 节点。完整参数、完整执行内容和安全版本继续由 `executionSpecHash` 覆盖，不能因为 UI 截断而缩小执行语义。

# 十八、SQLite Metadata 与 Output 文件分离（后续）

后续引入持久化时的设计是：

```text
Output → File
```

而不是：

```text
Output → SQLite
```

当前没有 SQLite 或持久日志；下面只描述后续数据流。

后续数据库每个 Execution 正常只需要：

```text
START
```

写一次。

结束：

```text
FINISH
```

写一次。

可能再更新：

```text
run_count
last_used_at
```

也就是说：

```text
几分钟的 Command
```

可能只有几次 DB Write。

这点预计负载对 SQLite 很轻，仍需在持久化单元验证。

# 十九、绝对不要每个 Output Chunk 写数据库（后续）

错误：

```text
stdout
↓
INSERT execution_output
stdout
↓
INSERT execution_output
stdout
↓
INSERT execution_output
```

这样会制造大量：

# 二十、SQLite WAL（后续）

WAL 用于减少 Reader 与 Writer 的相互阻塞；同时必须管理 WAL 大小和 Checkpoint，不能无限增长。

数据库配置：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
```

是后续 SQLite 单元的候选配置。

在 WAL 模式下使用 `synchronous=NORMAL`，可以降低正常事务路径的同步写延迟；代价是硬断电时最近事务的持久性弱于 `FULL`。是否接受该取舍必须在后续 SQLite/History 单元验证，当前不存在这一运行配置。

# 三十六、Performance Budget（当前硬边界与后续目标）

下表把当前代码硬边界和后续工程目标分开；工程目标不是产品承诺，也不是已经取得的测试证据：

| 场景 | 数值 | 状态 |
|---|---:|---|
| Rust Output Batch | 32 KiB 或 33 ms | 当前实现阈值 |
| React Output Buffer | 512 KiB 且最多 2048 个非空 Chunk | 当前硬上限 |
| Run response 前事件缓存 | 2048 事件、2048 非空 Fragment、512 KiB | 当前三重硬上限 |
| Preview Text | 32 KiB | 当前展示硬上限；Hash 仍覆盖完整 Spec |
| 冷启动到主界面可操作 | < 2s | 后续工程目标 |
| 热启动 | < 1s | 后续工程目标 |
| Command List 查询 | < 50ms | 后续工程目标 |
| 普通 Preview | < 50ms | 后续工程目标 |
| 自动 Preview 感知延迟 | < 250ms | 后续交互目标，当前带参数 Command 为手动 Preview |
| Run → Rust 开始 Spawn | < 100ms | 后续工程目标 |
| 虚拟化 Viewer 容量 | 约 5 MiB | 后续 Benchmark 候选，不是当前值 |
| Execution Log | 设置硬上限 | 后续持久日志目标 |
| Idle Memory | 尽量 < 150MB | 后续工程目标 |
| UI 主线程单次工作 | 尽量 < 16ms | 后续工程目标 |

注意这里：

```text
Run → Process 真正启动
```

会受到：

```text
Windows Defender
PowerShell
磁盘
```

影响。

所以真正应该测的是：

```text
CmdBox 自身耗时
```

而不是盲目要求总时间 `<100ms`。

# 三十七、最重要的性能原则：不要让“监控命令”影响“命令本身”（共同约束）

我认为这一条可以写进 CmdBox 的架构原则：

```text

      │
      │ highest priority
      ↓

Output Capture
      │
      ↓

Persistence
      │
      ↓

UI Rendering
```

当前优先级是 `命令执行 > Drain Output > Channel > UI`。后续加入持久日志后扩展为：

> **命令执行 > Drain Output > 保存日志 > 实时 UI。**

如果发生极端压力：

```text

```

甚至：

```text

```

但是：

```text
绝不能因为 UI 卡住导致 Command 卡住。
```

这对 CmdBox 非常重要。

## 当前已落地与后续冻结要求

当前 `CMD-02` 已落地：

```text
① Output
Process Reader
→ Output Aggregator
→ Batch
→ 每次 Run 专属 Tauri Channel

② React
Execution Output 不进入 Zustand
→ 独立有界 Chunk Buffer
→ 512 KiB + 2048 个非空 Chunk
→ 直接纯文本渲染

③ Renderer
render() 不返回 String
→ 返回 RenderedExecution

④ Preview
不再假设永远返回完整 renderedScript
→ previewText
→ fullSizeBytes
→ truncated
→ executionSpecHash 针对完整 Canonical Execution Spec
```

后续单元冻结要求：

```text
① Virtualized Viewer
必须在长输出 Benchmark 后引入，约 5 MiB 只是候选容量

② History / SQLite
executions 增加 log_size_bytes、output_truncated
Metadata 入 SQLite，Output 写独立有界日志

③ OutputPolicy
持久日志与 Viewer 均有独立硬上限
```

另外把一条产品级约束写死：

> **当前 Folder/Folders，以及后续 File/Files 参数的校验，都禁止递归扫描其内容。**

这一条对你的实际使用场景尤其重要。

后续 SQLite 设计保持 WAL、短事务、Metadata 入库和 Output 文件化，不提前复杂化；当前没有 SQLite、History 或持久日志。

这样处理以后，我认为我们已经提前封住了 **80% 以上未来最可能逼迫架构重做的性能问题**。剩下的性能优化应该依赖真实 benchmark，而不是继续预优化。
