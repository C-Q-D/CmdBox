# CmdBox 性能设计

## 文档职责

本文是 CmdBox 当前性能设计的唯一权威文档，约束外部进程输出、IPC、React 渲染、日志、SQLite、文件系统检查和性能验证。本文定义的是实现目标与预算，不表示相应能力已经通过测试。

总判断：

> **CmdBox 真正需要重点优化的不是模板渲染，也不是 SQLite，而是“外部进程输出 → Rust → IPC → React”这条链路，以及避免 CmdBox 自己干扰用户正在运行的重 I/O 命令。**

尤其你的核心场景是删除几十万/几百万小文件。CmdBox 最不能出现的情况就是：**命令本来 30 秒完成，因为我们疯狂记录日志、刷新 UI、扫描目录，结果变成 60 秒。**

---

## 一、先明确性能设计目标

我建议从第一天就把 CmdBox 的性能原则定义成：

> **CmdBox 的额外开销应该尽可能接近“直接在终端运行命令”。**

例如用户运行：

```cmd
rmdir /s /q "D:\huge-folder"
```

Terminal 需要：

```text
42.0 秒
```

CmdBox 最理想应该也是：

```text
42.x 秒
```

而不是：

```text
55 秒
```

所以我们需要区分两个性能指标：

```text
External Command Performance
```

和：

```text
CmdBox Overhead
```

前者主要由：

```text
PowerShell
CMD
Robocopy
SSD
NTFS
文件数量
杀毒软件
```

决定。

我们主要控制后者。

# 二、性能风险优先级

我目前会这样排：

| 优先级 | 模块 | 风险 |
|---|---|---|
| 🔴 P0 | stdout/stderr | 高频输出导致 CPU、内存、UI 卡顿 |
| 🔴 P0 | React 日志显示 | 大量文本导致 DOM/React 崩掉 |
| 🔴 P0 | 文件夹处理 | 错误地递归扫描大目录 |
| 🔴 P0 | Log 写盘 | 和删除/复制任务竞争磁盘 I/O |
| 🔴 P0 | IPC | 每行甚至每字符跨 Rust/WebView |
| 🟠 P1 | 内存 | 长任务 Output 无限增长 |
| 🟠 P1 | Template Preview | 参数变化造成重复渲染 |
| 🟠 P1 | SQLite | 高频小事务/错误保存 Output |
| 🟠 P1 | 多任务 | 锁竞争和多重 I/O |
| 🟡 P2 | 搜索 | Command 数量上千后的查询 |
| 🟡 P2 | 启动速度 | 启动时加载过多数据 |
| 🟡 P2 | Command Editor | 大 Template 编辑性能 |

下面分别定。

# 三、第一条铁律：绝对不要扫描目标文件夹

这条和你最开始的痛点直接相关。

比如用户选择：

```text
E:\comp\huge-folder
```

CmdBox **绝对不要为了展示这些东西去扫描目录：**

```text
文件数量：1,832,251
文件夹数量：42,321
大小：87.4 GB
```

因为为了算这些东西，我们自己就得先：

```text
递归遍历整个目录
```

这等于重现 Windows Explorer 删除前预扫描的问题。

因此用户选择文件夹以后，我们只做：

```text
Path Exists?
Is Directory?
Is Root?
Is Dangerous System Path?
```

这些都应该是接近 O(1) 的 metadata/path 操作。

不要做：

```text
calculateFolderSize()
countFiles()
walkDirectory()
scanPermissions()
```

所以快速删除 UI 最好只显示：

```text
3 个文件夹

D:\aaa
D:\bbb
D:\ccc
```

不要显示：

```text
共 2,938,281 个文件
共 124.7 GB
```

除非未来用户主动点击：

> 分析目录

那是另一个独立功能。

这个设计我建议现在就冻结。

---

# 四、最大的性能热点：stdout / stderr

假设一个命令每秒输出：

```text
10,000 行
```

如果我们这么做：

```text
Process
 ↓ 每行
Rust
 ↓ 每行 IPC
React
 ↓ setState
DOM
```

这个 App 很快就会卡。

高频 Streaming Data 使用 per-execution Tauri `Channel`，不使用普通全局事件机制。

但只使用 Channel 还不够。

我们需要：

```text
Process stdout
      ↓
   Reader
      ↓
 Output Aggregator
      ↓
   Batch / Chunk
      ↓
 Tauri Channel
      ↓
 React Buffer
      ↓
 Log Viewer
```

而不是：

```text
一行 = 一次 IPC
```

---

# 五、Output 必须 Batch

比如 Process 连续产生：

```text
aaa
bbb
ccc
ddd
...
```

不要：

```text
IPC 1 → aaa
IPC 2 → bbb
IPC 3 → ccc
IPC 4 → ddd
```

而应该聚合成例如：

```text
32 KB
```

或者：

```text
最多等待 20~50ms
```

然后：

```text
IPC

aaa
bbb
ccc
ddd
...
```

一次发送。

我建议初始策略：

```text
Flush if:

buffer >= 32KB
OR
elapsed >= 33ms
```

也就是 UI 最多大约：

```text
30 次更新 / 秒
```

已经足够感觉“实时”。

完全没有必要：

```text
1000 次 / 秒
```

这个参数以后 benchmark 可以调整，但 **Aggregator 层必须从第一版存在。**

---

# 六、Process Reader 不能被 UI 拖慢

这是一个非常重要的设计。

想象：

```text
robocopy.exe
     ↓
大量 stdout
     ↓
CmdBox UI 卡住
```

如果 Rust 没及时读取 stdout pipe，操作系统 pipe buffer 填满以后，理论上：

```text
robocopy
```

可能被迫等待。

也就是说：

> CmdBox 的日志 UI 反过来把真正的命令拖慢了。

这个是必须避免的。

所以架构应该：

```text
                     ┌→ Log Sink
Process → Fast Reader│
                     └→ UI Sink
```

Fast Reader 的首要职责是：

> **尽快 Drain stdout/stderr。**

UI 是否处理得过来是第二优先级。

极端情况下：

```text
UI 来不及
```

我们宁愿：

```text
少显示部分实时输出
```

也不应该：

```text
阻塞外部 Process
```

因此内部需要：

```text
bounded queue
+
output truncation
```

而不是无限排队。

---

# 七、日志 UI 和完整日志必须分离

基础数据流：

```text
Rust
 ↓
Channel
 ↓
React
```

还要进一步拆成：

```text
                ┌────────→ UI Ring Buffer
Process Output ─┤
                └────────→ Persistent Log
```

UI 永远只保留：

```text
最近 N MB
```

比如：

```text
5 MB
```

或者：

```text
最近 20,000 行
```

假设任务总共输出：

```text
800MB
```

React 绝不能持有这 800MB。

---

# 八、不要把 Execution Output 放 Zustand

这个最好现在就定下来。

Zustand 保存：

```text
executionId
status
startedAt
duration
exitCode
progress metadata
```

但是不要保存：

```text
完整 stdout
完整 stderr
```

否则：

```text
output append
↓
Zustand state change
↓
订阅组件 render
↓
大量对象/string allocation
```

很容易形成性能问题。

Output 应该有单独的：

```text
ExecutionOutputBuffer
```

例如：

```text
RingBuffer<OutputChunk>
```

它与业务 Store 分开。

---

# 九、不要不断做大字符串拼接

尤其不要：

```ts
output = output + newOutput;
```

运行几个小时以后：

```text
5MB
+ 5KB
+ 5KB
+ 5KB
...
```

会产生大量字符串复制。

更合理：

```text
[
  chunk1,
  chunk2,
  chunk3,
  ...
]
```

通过 Chunk / Ring Buffer 管理。

超过限制：

```text
drop oldest chunks
```

最终 UI 看到：

```text
[早期输出已从实时窗口移除]

...
最新输出
```

完整历史可以去读取 Log。

---

# 十、日志 Viewer 从一开始就不要做普通巨大 `<pre>`

最简单：

```tsx
<pre>{output}</pre>
```

小输出完全没问题。

但几十万行以后会很糟糕。

所以我们的 ExecutionOutput 最终应该是：

```text
Virtualized Log Viewer
```

只渲染屏幕附近的内容。

例如实际上有：

```text
20,000 行
```

DOM 里可能只有：

```text
100~300 行
```

这样滚动和选择文本才不会随着日志越来越多越来越卡。

因此 Output Viewer 建议从一开始就做成独立组件：

```text
ExecutionOutputViewer
```

不要让普通 `<Textarea>` 或 `<pre>` 成为架构依赖。

---

# 十一、Log File 也可能拖慢“快速删除”

这是一个更容易忽略的问题。

假设：

```text
Robocopy
```

正在疯狂读取：

```text
D:\
```

写：

```text
E:\
```

与此同时 CmdBox 又把每一条 stdout 写入：

```text
C:\Users\...\CmdBox\execution.log
```

这其实额外制造了磁盘 I/O。

如果 Output 特别大，就可能对真实任务造成干扰。

所以对于我们自己的内置 Command Block，原则应该是：

> **尽可能让命令本身少输出。**

例如你之前已经用了：

```text
/NP
```

这是对的。

针对内置高性能命令，我们可以进一步尽量避免：

```text
每个文件打印一行
```

而只保留真正有价值的信息。

例如“快速删除多个文件夹”：

```text
正在删除 D:\A
正在删除 D:\B
正在删除 D:\C
```

完全没必要输出：

```text
删除 file001
删除 file002
删除 file003
...
```

这里的性能收益可能比优化 Rust 代码大得多。

---

# 十二、Log 必须设置硬上限

我建议从架构上允许：

```text
UI buffer limit

Persistent log limit
```

例如初始值：

```text
UI:
5 MB

单次 Execution Log:
100 MB
```

100MB 不是最终产品数字，可以 benchmark 后调整。

关键是：

> **必须存在上限机制。**

达到上限后：

```text
[CmdBox: 日志超过限制，后续输出已省略]
```

但 Rust 仍然：

```text
继续 Drain stdout/stderr
```

只是停止存储。

否则用户随手运行：

```text
某个无限打印日志的脚本
```

几个小时以后 CmdBox 就可能：

```text
磁盘爆满
```

---

# 十三、Execution OutputPolicy

内部模型可以提前留出来：

```rust
struct OutputPolicy {
    ui_buffer_bytes: usize,
    persisted_log_bytes: u64,
}
```

暂时不需要在 Command Block Editor 里给用户设置。

它属于：

```text
App-level performance configuration
```

以后如果需要，再扩展：

```text
Normal
Quiet
Verbose
NoCapture
```

不会影响 Execution Engine。

# 十四、Preview 是第二个潜在热点

我们的设计是：

```text
用户修改参数
↓
preview_command_block
↓
Rust render
↓
React 显示
```

假设用户输入：

```text
D
D:
D:\
D:\P
D:\Pr
...
```

如果每敲一个字符都：

```text
IPC
DB Query
Parse Template
Render
Hash
IPC
React
```

没必要。

应该：

```text
Input
↓
Debounce 150~250ms
↓
Preview
```

File Picker 改变路径这种离散事件则可以立即 Preview。

# 十五、Template 不应该每次 Preview 都重新 Parse

我们现在支持：

```text
{{value}}

{{#if}}

{{#each}}
```

Template 应该先：

```text
Template String
↓
Parser
↓
AST
```

例如：

```text
[
 Text,
 Variable,
 Text,
 EachNode,
 ...
]
```

然后 Preview 只：

```text
AST
+
Parameters
↓
Renderer
```

而不是每一次：

```text
Parse
+
Render
```

所以内部最好设计：

```text
TemplateCache

key:
commandBlockId + revision
```

例如：

```text
0198xxx:revision-4
```

第一次使用：

```text
parse
```

之后：

```text
reuse AST
```

当 Command Block 更新：

```text
revision 4 → 5
```

Cache 自动失效。

这个优化现在设计非常便宜，但以后加会涉及 Template Engine 重构，所以值得现在做。

# 十六、大量 Folder 参数也需要保护

例如正常：

```text
3 个 folders
```

非常轻。

但理论上用户可以一次拖：

```text
30,000 个文件夹
```

进来。

然后 Template：

```powershell
{{#each paths}}
Remove-Item ...
{{/each}}
```

可能生成数 MB Script。

所以应该有：

```text
Rendered Script Size Guard
```

比如初始：

```text
8 MB
```

超过以后不允许直接无限渲染。

更重要的是，我们可以提前把内部 Runner 输入定义抽象成：

```text
RenderedExecution
```

而不是写死：

```text
String
```

未来就可以支持：

```text
RenderedExecution
├─ Script
└─ Auxiliary Files
```

例如极端情况下：

```text
30,000 paths
```

可以生成：

```text
paths.json
```

然后 Script 读取路径文件。

MVP 不需要实现，但架构上不要把：

```rust
fn render() -> String
```

写死成永远只能一个 String。

可以：

```rust
fn render() -> RenderedExecution
```

第一版：

```text
RenderedExecution {
    script
}
```

未来扩展不需要改 Execution Engine。

这个我建议现在调整。

---

# 十七、Preview 不应该无限显示完整 Script

类似问题。

如果用户选择：

```text
10,000 个目录
```

Rendered Script：

```text
2MB
```

然后前端展示：

```text
2MB syntax highlighted code
```

也会非常慢。

所以 Preview Response 建议改成：

```ts
interface PreviewCommandResponse {
  commandBlockId: string;

  revision: number;

  runner: RunnerType;

  parameterSummaries: PreviewParameterSummary[];

  previewText: string;

  fullSizeBytes: number;

  truncated: boolean;

  previewHash: string;

  riskLevel: RiskLevel;

  actionLabel: string;

  safety: PreviewSafetyDecision;
}

interface PreviewParameterSummary {
  parameterKey: string;
  label: string;
  displayValues: string[];
  totalCount: number;
  truncated: boolean;
}
```

比如：

```text
命令预览

Remove-Item 'D:\A' ...
Remove-Item 'D:\B' ...
Remove-Item 'D:\C' ...
...

已省略其余 9,997 项
```

真正 Hash 仍然针对：

```text
完整 Script
```

这样：

```text
安全校验
```

和：

```text
UI 性能
```

可以同时保证。

对于 destructive Command，更重要的是单独展示：

```text
目标：10,000 个文件夹
```

而不是要求用户阅读 2MB PowerShell。

`parameterSummaries` 同样必须有界：`totalCount` 表达完整规范化数量，`displayValues` 只返回受控数量并用 `truncated` 标记省略。Safety Warning 也应按稳定类别聚合并设置返回上限，不能把一万个目标转换成一万个 UI 节点。完整参数、完整执行内容和安全结论继续由 Preview Hash 覆盖，不能因为 UI 截断而缩小执行语义。

# 十八、SQLite 其实不会是主要瓶颈——前提是我们别错误使用

我们已经决定：

```text
Output → File
```

而不是：

```text
Output → SQLite
```

这个决定非常重要。

数据库每个 Execution 正常只需要：

```text
START
```

写一次。

结束：

```text
FINISH
```

写一次。

可能再更新：

```text
run_count
last_used_at
```

也就是说：

```text
几分钟的 Command
```

可能只有几次 DB Write。

这点负载对 SQLite 很轻。

# 十九、绝对不要每个 Output Chunk 写数据库

错误：

```text
stdout
↓
INSERT execution_output
stdout
↓
INSERT execution_output
stdout
↓
INSERT execution_output
```

这样会制造大量：

```text
transactions
locking
WAL
fsync
```

正确：

```text
stdout
↓
Log File

metadata
↓
SQLite
```

# 二十、WAL 继续保留

WAL 用于减少 Reader 与 Writer 的相互阻塞；同时必须管理 WAL 大小和 Checkpoint，不能无限增长。

数据库配置：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
```

仍然合理。

在 WAL 模式下使用 `synchronous=NORMAL`，降低正常事务路径的同步写延迟；代价是硬断电时最近事务的持久性弱于 `FULL`。对于可重建或可接受最近记录损失的本地执行历史，这是当前采用的取舍。

# 二十一、不要在 Startup 做数据库重活

打开 App 时我们只加载：

```text
Categories

CommandBlockSummary
```

不要加载：

```text
所有 CommandBlock 完整 Config
所有 Executions
所有 Logs
所有 Parameter States
```

所以：

```text
Startup
↓
DB Open
↓
Migration
↓
Categories
↓
最近 Command Summary
↓
Window Ready
```

用户点击某一个 Command：

```text
get_command_block(id)
```

才加载：

```text
Template
Parameters
Config
Last Values
```

---

# 二十二、启动时绝对不要扫描 Log Directory

以后用户可能有：

```text
20,000 Execution Logs
```

启动时如果：

```text
read_dir
↓
stat 所有文件
↓
计算大小
```

启动时间就会越来越慢。

所以 `executions` 表建议增加：

```text
log_size_bytes
```

任务完成时，我们已经知道写了多少：

```text
37,282 bytes
```

直接记录。

清理历史可以：

```sql
SELECT ...
ORDER BY started_at ASC
```

找到最老 Log 删除。

完全不需要启动时扫描磁盘。

这也是一个值得现在加进去的字段。

# 二十三、History 永远分页

禁止：

```text
SELECT * FROM executions
```

然后一次返回：

```text
20,000 条
```

应该：

```text
LIMIT 50
```

下一页：

```text
cursor / offset
```

UI：

```text
Infinite Scroll
```

或者分页。

# 二十四、Command List 也只传 Summary

Command List 继续只传 Summary。

左边列表：

```text
快速删除
高速复制
Git Pull
...
```

完全不需要把：

```text
template
parameters
environment
```

都加载过来。

所以：

```text
CommandBlockSummary
```

继续保留。

# 二十五、Search 暂时不要上复杂全文检索

用户哪怕：

```text
500 Command Blocks
```

SQLite：

```sql
LIKE
```

都不是问题。

现在提前做 FTS：

```text
FTS index
tokenizer
sync trigger
migration
```

反而增加复杂度。

但 Search 要：

```text
debounce 100~150ms
```

并限制：

```text
LIMIT 50
```

不要用户每敲一个字：

```text
SELECT → 1000 rows → React render
```

---

# 二十六、数据库锁必须短

我们之前设计：

```rust
Arc<Mutex<Connection>>
```

第一版可以继续。

但必须遵守：

```text
Lock
↓
执行短 SQL
↓
Unlock
```

绝对不能：

```text
Lock Database
↓
await PowerShell
↓
await stdout
↓
几分钟以后 unlock
```

同样：

```text
ExecutionManager Mutex
```

也只允许：

```text
insert
get
remove
```

不能持锁等待 Process。

---

# 二十七、多任务时最容易出现锁设计问题

例如：

```text
Execution A
Execution B
Execution C
```

同时输出。

不要所有任务争抢一个：

```text
Global Output Mutex
```

应该：

```text
Execution A → OutputAggregator A
Execution B → OutputAggregator B
Execution C → OutputAggregator C
```

只有：

```text
ExecutionManager HashMap
```

是全局。

这样一个疯狂输出的任务不会拖另一个。

---

# 二十八、每个 Execution 自己写自己的 Log

例如：

```text
execution-A.log
execution-B.log
execution-C.log
```

不要：

```text
GlobalLogWriter
```

串行处理所有任务的 stdout。

应用自己的 Debug Log：

```text
cmdbox.log
```

和：

```text
Execution Output
```

也必须分开。

---

# 二十九、Process 状态全部事件驱动，不轮询

不要：

```text
每 100ms
↓
is process alive?
↓
is process alive?
↓
is process alive?
```

Rust 应：

```text
process.wait().await
```

用户点击 Cancel 才：

```text
Job Object terminate
```

UI 计时器：

```text
1 秒一次
```

更新：

```text
01:32
```

完全够了。

---

# 三十、前端需要严格控制 Re-render 边界

例如页面：

```text
CommandRunner
├─ ParameterForm
├─ Preview
├─ ExecuteButton
└─ Output
```

如果 Output 每 33ms 更新：

```text
CommandRunner 整棵树
```

都 render 一次，就很浪费。

所以 Output 必须形成独立更新边界：

```text
ParameterForm
        不更新

Preview
        不更新

ExecuteButton
        偶尔更新

ExecutionOutput
        高频更新
```

这也是为什么不把 Output 放全局 Zustand。

---

# 三十一、Syntax Highlight 也要小心

Command Preview 以后可能想做：

```text
PowerShell 彩色高亮
```

小脚本没问题。

但是：

```text
1MB Script
```

做完整 AST Syntax Highlight 可能相当耗 CPU。

所以：

```text
previewText <= 一定大小
```

才启用高亮。

大 Preview：

```text
Plain Text
```

或者截断。

这是典型“锦上添花不能影响运行”的功能。

---

# 三十二、Windows Encoding 要做增量 Decoder

这个除了正确性，也影响性能。

不能每读：

```text
4KB
```

就：

```rust
String::from_utf8_lossy(...)
```

因为 Unicode 字符可能刚好跨 Chunk。

例如：

```text
Chunk 1：中文字节前半
Chunk 2：后半
```

必须使用：

```text
Streaming Decoder
```

状态保留在 Execution Runner 中。

而且：

```text
bytes
↓
decode
↓
String
```

只做一次。

不要：

```text
Rust decode
↓
JSON
↓
JS 再重新处理
```

---

# 三十三、Temp Script 的性能先不要过度优化，但留抽象

我们现在：

```text
Render
↓
Temp .ps1
↓
powershell.exe -File ...
```

这个方案继续。

可能未来发现：

```text
创建临时文件
+
杀毒软件扫描
+
PowerShell startup
```

对非常短的命令有明显延迟。

但不值得现在为了：

```text
20ms
```

重新引入复杂：

```text
-Command quoting
```

我们只需要让 Runner 接收：

```rust
ExecutionArtifact
```

而不是直接写死：

```rust
PathBuf
```

未来可以：

```rust
enum ExecutionArtifact {
    ScriptFile(...),
    Inline(...),
}
```

MVP：

```text
ScriptFile only
```

以后 profile 真证明需要时再增加 Inline。

架构不用变。

---

# 三十四、PowerShell 启动本身可能比 CmdBox 慢

例如：

```text
echo hello
```

真正最慢的可能不是：

```text
Rust
IPC
React
```

而是：

```text
powershell.exe startup
```

所以一定要记录几个时间点：

```text
T0 点击 Run
T1 Validation 完成
T2 Render 完成
T3 Process Spawn
T4 First Output
T5 Process Exit
```

最后我们能知道：

```text
Preview 3ms
Render 1ms
Spawn 214ms
Command 28ms
```

否则以后用户说：

> CmdBox 怎么感觉慢？

开发者只能猜。

# 三十五、从第一版加入性能埋点，但只做本地 tracing

不用用户遥测。

Rust `tracing` 可以记录：

```text
preview_duration_ms
template_render_ms
db_query_ms
spawn_latency_ms
first_output_ms
execution_duration_ms
stdout_bytes
stderr_bytes
ipc_batch_count
log_bytes
```

Development Build：

```text
详细记录
```

Release：

```text
减少详细日志
```

这样性能问题可以直接 profile。

# 三十六、我们应该建立 Performance Budget

我建议先把它作为工程目标，而不是产品承诺：

| 场景 | 初始工程目标 |
|---|---:|
| 冷启动到主界面可操作 | < 2s |
| 热启动 | < 1s |
| Command List 查询 | < 50ms |
| 普通 Preview | < 50ms |
| 输入后 Preview 更新 | < 250ms 感知延迟 |
| Run → Rust 开始 Spawn | < 100ms |
| Output UI 更新频率 | ≤ 30 次/s |
| 单次 IPC Output Chunk | ~32–64KB |
| UI Output Buffer | ~5MB |
| Preview UI | 默认 ≤ 256KB |
| Execution Log | 设置硬上限 |
| Idle Memory | 尽量 < 150MB |
| UI 主线程单次工作 | 尽量 < 16ms |

注意这里：

```text
Run → Process 真正启动
```

会受到：

```text
Windows Defender
PowerShell
磁盘
```

影响。

所以真正应该测的是：

```text
CmdBox 自身耗时
```

而不是盲目要求总时间 `<100ms`。

---

# 三十七、最重要的性能原则：不要让“监控命令”影响“命令本身”

我认为这一条可以写进 CmdBox 的架构原则：

```text
Command Execution
      │
      │ highest priority
      ↓

Output Capture
      │
      ↓

Persistence
      │
      ↓

UI Rendering
```

优先级应该永远是：

> **命令执行 > Drain Output > 保存日志 > 实时 UI。**

如果发生极端压力：

```text
UI 可以少显示
```

甚至：

```text
Log 可以截断
```

但是：

```text
绝不能因为 UI 卡住导致 Command 卡住。
```

这对 CmdBox 非常重要。

---

# 三十八、你的“超大文件夹删除”要专门做性能基准

等真正进入开发时，我们第一套 Benchmark 不应该是 Todo Demo。

而应该创建几组真实目录：

```text
Case A
10,000 个 1KB 文件

Case B
100,000 个 1KB 文件

Case C
500,000 个空文件

Case D
10,000 个深层嵌套目录

Case E
中文路径 + 长路径
```

分别测试：

```text
直接 Terminal
```

和：

```text
CmdBox
```

我们关注的不是哪个 Windows 删除命令最快，而是：

```text
CmdBox / Terminal
```

之间的 overhead。

例如：

```text
Terminal        31.2s
CmdBox          31.8s

overhead         0.6s
                 1.9%
```

这才是核心指标。

## 冻结的架构要求

以下要求在实现前固定：

```text
① Output
Process Reader
→ Output Aggregator
→ Batch
→ Tauri Channel

② React
Execution Output 不进入 Zustand
→ 独立 Ring Buffer + Virtualized Viewer

③ Renderer
render() 不返回 String
→ 返回 RenderedExecution

④ History
executions 新增
log_size_bytes
output_truncated

⑤ Preview
不再假设永远返回完整 renderedScript
→ previewText
→ fullSizeBytes
→ truncated
→ previewHash 针对完整执行内容
```

另外把一条产品级约束写死：

> **Folder / File 参数的校验禁止递归扫描其内容。**

这一条对你的实际使用场景尤其重要。

SQLite 保持 WAL、短事务、Metadata 入库和 Output 文件化，不提前复杂化。

这样处理以后，我认为我们已经提前封住了 **80% 以上未来最可能逼迫架构重做的性能问题**。剩下的性能优化应该依赖真实 benchmark，而不是继续预优化。
