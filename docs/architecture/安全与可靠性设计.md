# CmdBox 安全与可靠性设计

## 文档职责

本文是 CmdBox 当前安全与可靠性设计的唯一权威文档。目标是在 UI、参数、系统环境、进程、日志或数据库发生异常时，仍然保持执行行为可解释、可控制，不让用户确认的操作意外变成另一项操作。

## 当前实现基线（CMD-02）

- 当前默认 Registry 只有 `windowsPowerShell` 与 `cmd` 两条 normal 风险参数回显 Built-in，并已实现六类 Typed Parameter、完整 `executionSpecHash` 复验、Job Object、一次性 Run 授权、per-run Channel、Output、Cancel 与唯一 Lifecycle 终态。
- 当前没有破坏性 Command、Path Fingerprint、Structured SafetyPolicy、Outcome Policy 解释、History、SQLite、持久日志或 Built-in/User Command 编辑能力。本文涉及这些内容的章节是后续 MVP 必须满足的安全设计，不是 `CMD-02` 已运行的公共契约。
- 当前实现和真实 Windows/Tauri 证据统一见[测试与验收](../testing/测试与验收.md)；尚未取证的后续能力不得写成已实现。

## 1. 目标

CmdBox 的安全目标不是阻止用户运行危险命令。

因为 CmdBox 本质上就是：

> 一个允许用户执行本地 Shell Command 的工具。

真正需要保证的是：

```text
用户看到什么
=
CmdBox 实际执行什么
```

以及：

```text
用户要求执行 A
绝不能因为路径、状态、进程或 UI Bug
意外执行成 B
```

第一阶段重点防范：

| 风险 | 要求 |
|---|---|
| 参数注入 | Typed Parameter + Shell Serializer |
| 误删系统路径 | Path Safety Guard |
| Preview 过期 | Revision + `executionSpecHash` |
| 路径被替换 | Path Fingerprint |
| 双击执行两次 | Duplicate Execution Guard |
| Cancel 只杀父进程 | Process Tree 管理 |
| CmdBox 崩溃后任务继续 | Job Object Kill-on-close |
| 临时脚本被篡改 | Temp Script Integrity |
| Runner 环境不一致 | Deterministic Runner |
| PowerShell 等待交互 | NonInteractive |
| 工具特殊 Exit Code | Outcome Policy |
| 部分失败却显示成功 | Explicit Exit Semantics |
| 日志/数据库失败拖垮命令 | Failure Isolation |

---

# 2. 明确威胁模型

CmdBox MVP **保护的是误操作和软件缺陷**。

包括：

```text
用户输错参数
UI 状态过期
路径异常
Command Block 被修改
重复点击
进程异常
App 崩溃
数据库异常
恶意 Output
```

但 MVP 不承诺防御：

```text
用户故意创建恶意 Command Block
已经拥有当前用户权限的恶意本地程序
Administrator / SYSTEM 级攻击者
已经被攻陷的操作系统
```

这一点非常重要。

例如用户自己创建：

```powershell
Remove-Item C:\xxx -Recurse -Force
```

CmdBox 不能声称：

> “这个脚本一定安全。”

CmdBox 能保证的是：

> 我不会偷偷改变你的参数，也不会让 Preview 和实际执行产生差异。

---

# 3. Rust Core 是安全边界

架构继续保持：

```text
┌─────────────────────┐
│      WebView        │
│ React / TypeScript  │
└──────────┬──────────┘
           │
       Typed IPC
           │
┌──────────▼──────────┐
│      Rust Core      │
│                     │
│ Validation          │
│ Template            │
│ Safety              │
│ Process             │
│ Database            │
└─────────────────────┘
```

Tauri 的 WebView 与 Rust Core 属于不同信任边界，系统资源只通过明确暴露的 IPC 能力进入前端。

因此继续禁止：

```text
execute_shell(string)
spawn_process(string)
kill_pid(number)
```

这种通用 IPC。

---

# 4. WebView 不加载远程代码

MVP 默认：

```text
Remote JavaScript     禁止
Remote HTML           禁止
CDN Script            禁止
Remote Tauri Access   禁止
```

所有 React 代码和依赖跟随应用打包。

WebView 不加载远程脚本，并尽可能收紧 CSP。

因此 CmdBox 第一版：

```text
default-src 'self'
```

为基础建立 CSP。

即使以后增加：

```text
AI
Update Check
Cloud Sync
```

网络请求也应该优先经过 Rust Core，而不是让远程页面进入高权限 WebView。

# 5. Command Block 增加 Origin

新增：

```ts
type CommandOrigin =
  | "builtin"
  | "user";
```

Built-in Command：

```text
CmdBox 官方提供
Safety Profile 固定
Template 固定
经过测试
```

User Command：

```text
用户自己创建
用户自己承担脚本语义
CmdBox 仍进行参数、Preview、路径基础保护
```

Built-in Command 不允许直接修改。

用户点击：

```text
编辑
```

实际上执行：

```text
复制为自定义命令
```

得到：

```text
origin = user
```

这样不会出现：

```text
官方安全命令
↓
用户改掉 Template
↓
仍然挂着“官方安全规则”
```

---

# 6. Safety 不能只有 destructive: true

单独使用：

```ts
riskLevel:
  "normal" | "destructive"
```

太粗。

改为：

```rust
enum SafetyPolicy {
    Generic,
    DeletePaths(DeletePathPolicy),
    CopyPaths(CopyPathPolicy),
    MovePaths(MovePathPolicy),
}
```

风险级别仍然存在：

```text
normal
destructive
```

但它负责 UI。

真正安全逻辑来自：

```text
SafetyPolicy
```

例如：

```text
Windows 快速删除多个目录

SafetyPolicy
=
DeletePaths
```

Rust 因此明确知道：

> `paths` 参数代表删除目标。

不需要通过解析 PowerShell 猜测。

---

# 7. DeletePathPolicy

概念：

```rust
struct DeletePathPolicy {
    parameter_key: String,

    require_absolute: bool,

    require_exists: bool,

    reject_reparse_point: bool,

    block_volume_root: bool,

    block_system_paths: bool,

    fingerprint_target: bool,
}
```

这样 SafetyGuard 针对：

```text
结构化参数
```

工作。

而不是分析：

```powershell
Remove-Item ...
```

---

# 8. Path Safety 必须分成两步

路径不能只做：

```text
Path.exists()
```

完整流程：

```text
用户输入 Path
      ↓
Syntax Normalize
      ↓
Absolute Path
      ↓
Filesystem Metadata
      ↓
Reparse Point Check
      ↓
Final Path Resolution
      ↓
Protected Path Check
      ↓
Path Fingerprint
```

但仍然：

> **禁止递归扫描目录内容。**

所以这套检查与目录里面有：

```text
10 个文件
```

还是：

```text
1000 万个文件
```

基本无关。

---

# 9. Path Normalize

Windows 下至少处理：

```text
.
..
末尾分隔符
大小写比较
DOS Path
UNC Path
Extended Path
```

Destructive Built-in 默认拒绝用户直接输入危险 Device Namespace，例如：

```text
\\.\...
\\?\GLOBALROOT\...
\??\...
```

普通：

```text
C:\Projects\Test
```

以及：

```text
\\server\share\folder
```

才属于正常路径输入范围。

内部 Rust 可以转换为 Win32 Extended Path 使用。

---

# 10. Final Path

不能只比较字符串。

例如：

```text
C:\Something
```

可能实际指向另外一个位置。

Windows 使用 `GetFinalPathNameByHandleW` 获取打开对象解析后的最终路径；对于符号链接，最终路径指向真实目标。

SafetyGuard 应根据：

```text
Input Path
+
Final Path
```

共同判断。

---

# 11. Reparse Point

Windows：

```text
Junction
Symbolic Link
Mount Point
```

底层都与 Reparse Point 机制有关。

`GetFileAttributes` 可以通过 `FILE_ATTRIBUTE_REPARSE_POINT` 判断目标是否具有 Reparse Point。

MVP 对：

```text
Builtin + DeletePaths
```

采用安全优先策略：

```text
顶层目标是 Reparse Point
→ 默认拒绝快速删除
```

显示：

```text
该目录是符号链接或 Junction。
为了避免删除目标不明确，CmdBox 未执行此操作。
```

以后可以专门增加：

```text
删除链接本身
```

这种 Command Block。

---

# 12. 不递归寻找内部 Reparse Point

这里需要非常明确。

CmdBox **不会为了安全检查而递归扫描目标目录**。

因为：

```text
扫描 300 万个文件
```

本身就破坏了“快速删除”的核心价值。

因此 SafetyGuard 保证的是：

> **目标根路径安全。**

不是：

> **对整个目录树建立完整 Filesystem Sandbox。**

内部 Junction/Symlink 的行为必须纳入具体 Built-in Command 的 Windows 实测。

---

# 13. Protected Paths 分三级

不能简单：

```text
dangerous = true / false
```

定义：

```text
NORMAL
HIGH_RISK
CRITICAL
```

### CRITICAL

直接拒绝 Built-in destructive command。

例如：

```text
C:\
D:\

\\server\share\

Windows Directory

System Directory

Program Files

ProgramData

当前 User Profile 根目录

CmdBox App Data
```

系统级目录应通过 Windows Known Folder / System API 获取，而不是硬编码：

```text
C:\Windows
```

---

# 14. HIGH_RISK

例如精确选择：

```text
Desktop 根目录
Documents 根目录
Downloads 根目录
OneDrive 根目录
```

不直接禁止。

但需要强化确认：

```text
你正在永久删除：

C:\Users\User\Documents

请输入：
DELETE
```

这种确认只针对极少数异常路径。

正常：

```text
C:\Users\User\Documents\OldProject
```

不会触发。

所以不会影响日常效率。

---

# 15. 路径集合需要 Normalize

例如用户一次选择：

```text
D:\Project

D:\Project\build

D:\Project\build\old
```

如果全部执行：

```text
Delete Project
Delete build
Delete old
```

后两个一定产生奇怪的：

```text
Path Not Found
```

因此 DeletePaths 在 Preview 前进行：

```text
Duplicate Removal
+
Ancestor Collapse
```

得到：

```text
D:\Project
```

UI 提示：

```text
2 个子目录已包含在父目录中，因此不会重复执行。
```

---

# 16. Path Fingerprint

仅仅 Preview Final Path 还不够。

考虑：

```text
Preview

D:\OldBuild
```

用户看到没问题。

然后 Preview 到 Run 之间：

```text
D:\OldBuild
```

被删除并重新建立成了另一个目录。

甚至变成：

```text
Junction
```

因此 destructive built-in 在 Preview 时保存：

```text
PathFingerprint
```

概念：

```rust
struct PathFingerprint {
    normalized_path: PathBuf,

    final_path: PathBuf,

    volume_id: ...,

    file_id: ...,

    is_reparse_point: bool,
}
```

Run 时重新读取。

如果：

```text
Preview Fingerprint
!=
Run Fingerprint
```

返回：

```text
TARGET_CHANGED
```

要求重新 Preview。

---

# 17. 这不需要扫描文件夹

Fingerprint 是目录对象本身的身份。

所以：

```text
D:\huge-folder
```

里面有几百万文件也没关系。

只读取：

```text
目录 Handle
Metadata
File ID
```

因此不违反“禁止递归扫描目录内容”的性能原则。

---

# 18. Execution Spec Hash

当前 `CMD-02` 的 `executionSpecHash` 对以下完整 Canonical Execution Spec 做稳定 length-prefixed 编码后计算 SHA-256：

```text
format
schemaVersion
commandBlockId
revision
runnerType
runnerExecutable
runnerFixedOptions
runnerRawCommandTail
artifactHash
normalizedParameters
workingDirectory
explicitEnvironment
internalEnvironment
safetyPolicyVersion
outcomePolicyVersion
```

当前 Hash 尚不包含 `pathFingerprints`，因为默认两条 normal Echo 不操作破坏性目标。后续永久删除单元必须把重新取得的目标身份和 Path Fingerprint 纳入 Canonical Execution Spec，再递增 `schemaVersion`；不能在不升级 Schema 的情况下暗改 Hash 语义。

这样：

```text
Preview
```

实际代表的是：

> **整个 Execution Spec。**

不是单纯脚本文本。

---

# 19. Run 必须重新计算全部信息

绝不能：

```text
Preview
↓
缓存 Rendered Script
↓
Run 直接执行缓存
```

而应该：

```text
Run
↓
重新读取 Command Block
↓
重新校验参数
↓
重新校验路径
↓
重新生成 Fingerprint
↓
重新 Render
↓
重新生成 ExecutionSpec
↓
重新 Hash
```

当前 normal Echo 执行适用其中的 Definition、参数、Runner、Artifact、环境和完整 Hash 复验；路径身份、Fingerprint 与 Destructive Safety Guard 是后续永久删除单元在同一路径上增加的步骤。

只有：

```text
newExecutionSpecHash == executionSpecHash
```

才启动 Process。

---

# 20. Duplicate Execution Guard

用户很可能：

```text
双击
```

或者界面卡了一下再次点击：

```text
永久删除
永久删除
```

所以 UI Disable Button 还不够。

Rust 对 destructive execution 增加：

```text
Single Flight Guard
```

如果：

```text
相同 executionSpecHash
```

当前已经存在一个 Running Execution：

```text
第二次 Run
→ DUPLICATE_EXECUTION
```

这样不会因为 UI Bug 真的删两次。

---

# 21. Windows Process 必须属于 Job Object

这是最重要的底层可靠性要求之一。

Windows Job Object 可以把一组进程作为整体管理；设置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 后，最后一个 Job Handle 被关闭时，Job 中关联的所有进程都会被终止。

因此：

```text
Execution
    ↓
Job Object
    ↓
powershell.exe / cmd.exe
    ↓
child
    ↓
grandchild
```

全部属于一个 Execution。

---

# 22. 必须避免 Process Assignment Race

不能简单：

```text
spawn process
↓
过一会儿
↓
AssignProcessToJobObject
```

因为在这个间隔中：

```text
child
```

已经可能继续创建自己的子进程。

所以 Windows Runner 应采用：

```text
Create Process Suspended
        ↓
Assign Job Object
        ↓
Resume Process
```

Windows Job API 支持把 Process 分配到 Job，Process 也可以以 Suspended 状态创建。

因此 Windows 平台的实现要求是：

> Windows Process Manager 不应完全依赖简单的 `tokio::process::Command`。

Windows 平台可能需要通过：

```text
windows crate
+
CreateProcessW
+
Job Object API
```

建立底层 Process。

这是值得现在定下来的。

---

# 23. 不允许 Process Breakaway

MVP 的 Job Object 不启用：

```text
BREAKAWAY_OK
```

原则：

> Command 如果不能可靠地被 CmdBox 管理，就宁愿启动失败，也不要偷偷逃离 Execution Job。

未来真的遇到某些工具必须 Breakaway，再针对具体 Runner 设计。

---

# 24. Cancel 的真实语义

用户点击：

```text
终止任务
```

不是：

```text
kill shell.exe
```

而是：

```text
Terminate Execution Job
```

UI：

```text
RUNNING
↓
CANCELLING
↓
CANCELLED
```

只有 Rust 确认整个 Job 已结束以后：

```text
CANCELLED
```

才能显示。

---

# 25. CmdBox 崩溃时也终止任务

Job Object Handle 由 CmdBox Rust Core 持有。

如果 CmdBox：

```text
正常退出
崩溃
被 Task Manager 结束
```

操作系统关闭 Handle。

因为 Job 设置：

```text
KILL_ON_JOB_CLOSE
```

其关联 Process 会一起终止。

这正是我们需要的行为：

> **CmdBox 不在了，它启动的一次性任务也不应该继续失控运行。**

---

# 26. Frontend 崩溃与 Rust 崩溃区别

如果只是：

```text
React/WebView
```

异常，但 Rust Core 仍然存在：

```text
Execution
```

不应因为 Channel 断开就自动结束。

Execution Ownership 属于：

```text
Rust ExecutionManager
```

而不是 React Component。

后续恢复单元中，UI 重建后可以通过：

```text
list_active_executions()
```

重新显示：

```text
当前仍在运行的任务
```

截至 `CMD-02` 尚未实现 `list_active_executions` 或 History 恢复；当前已实现的保证是 Channel 断开不会取消或阻塞 Rust Execution，整个 Rust App Process 退出时则由 Job Object 终止受管进程树。

但如果整个 Rust App Process 退出：

```text
Job Object
→ Kill
```

---

# 27. Runner 必须确定，不使用“自动优先 pwsh”

禁止采用：

```text
powershell
↓
有 pwsh → pwsh
↓
没有 → powershell.exe
```

从可靠性角度不好。

因为同一个 Command Block：

```text
今天
Windows PowerShell 5.1

明天安装 PowerShell 7

突然变成 PowerShell 7
```

执行语义可能发生变化。

当前生成契约严格使用：

```ts
type RunnerType =
  | "windowsPowerShell"
  | "cmd";
```

PowerShell 7、Bash、Zsh 只有在后续扩展生成契约、Serializer、确定解析和真实宿主门禁后才能加入，例如：

```text
powershell7
bash
zsh
```

它们当前不是合法 wire value，也不能由“自动优先”逻辑替换已确认 Runner。

---

# 28. Runner 不通过 PATH 找自己

例如 CMD：

不要：

```text
PATH → cmd.exe
```

应该由 Windows System API 获取：

```text
System32\cmd.exe
```

Windows PowerShell 同理解析固定系统位置。

后续 Execution History 保存：

```text
runnerType
runnerExecutable
runnerVersion
```

以后出现：

```text
为什么这次执行行为不同？
```

才能追踪。

---

# 29. PowerShell 执行方式

Windows PowerShell 使用：

```text
-NoLogo
-NoProfile
-NonInteractive
-ExecutionPolicy Bypass
-File <script>
```

`-NoProfile`：

避免用户 Profile：

```text
Alias
Function
Module
Environment modification
```

影响 CmdBox。

`-NonInteractive`：

如果脚本试图：

```text
Read-Host
确认输入
```

应该失败。

而不是：

```text
CmdBox 永久卡住等待 stdin
```

---

# 30. Execution Policy 不修改系统

CmdBox 绝不能调用：

```powershell
Set-ExecutionPolicy ...
```

修改：

```text
CurrentUser
LocalMachine
```

配置。

临时 Script 使用：

```text
-ExecutionPolicy Bypass
```

只针对当前 PowerShell Process。

Process Scope 只影响当前会话，进程结束后即消失；Group Policy 的 MachinePolicy/UserPolicy 优先级更高，不会被这种会话级设置覆盖。

因此：

```text
不永久修改用户系统
+
仍然尊重企业 Group Policy
```

---

# 31. PowerShell Script Encoding

这件事必须现在确定。

Windows PowerShell 5.1 读取没有 BOM 的脚本时，非 ASCII 字符可能按 Legacy ANSI 编码解释，因此含非 ASCII 字符的临时脚本统一使用 UTF-8 BOM。

因此：

```text
windowsPowerShell
.ps1
```

统一生成：

```text
UTF-8 with BOM
```

避免：

```text
C:\项目\测试
```

这种路径被错误解释。

---

# 32. CMD Encoding 作为发布 Gate

CMD 对：

```text
Unicode Batch File
Code Page
External Program Output
```

处理没有 PowerShell 那么统一。

因此 CMD Runner 上线之前必须通过：

```text
中文路径
日文路径
Emoji
空格
单引号
双引号
&
%
^
!
```

完整测试。

如果不能做到确定行为：

> 宁愿推迟某些 CMD Template，也不要表面支持但在非英文路径下产生错误。

# 33. Long Path

CmdBox 自己需要声明：

```xml
longPathAware=true
```

CmdBox 的 Windows Manifest 声明 `longPathAware=true`，并使用支持长路径的 Win32 API。

但同时必须明确：

> CmdBox 支持长路径，不代表被启动的每一个外部 CLI 都支持长路径。

所以 History 中如果外部程序失败：

```text
External Tool Limitation
```

不能被 CmdBox 吞掉。

# 34. MVP 不提供自动 UAC 提权

第一版明确：

```text
Run as Administrator
```

不是 Command Block 能力。

原因是：

```text
普通 Rust Core
↓
Elevated Process
```

会引入新的：

```text
Privilege Boundary
IPC
Pipe Security
Process Ownership
Output Capture
UAC
```

问题。

所以 MVP：

```text
当前 CmdBox 是什么权限
Command 就是什么权限
```

---

# 35. 不自动把整个 App 提权

尤其不要：

```text
发现 Access Denied
↓
自动把 CmdBox 以管理员重新启动
```

因为这会让：

```text
WebView
React
整个 Rust Core
```

全部获得 Administrator 权限。

未来如果确实需要 Admin Command：

正确方向是：

```text
Normal CmdBox
       ↓
Narrow IPC
       ↓
Signed Elevated Helper
```

而不是：

```text
整个 UI 永久 Admin
```

# 36. 用户手动以管理员启动 CmdBox

这种情况无法完全禁止。

但必须检测：

```text
Current Process Elevated
```

然后整个窗口明显显示：

```text
⚠ 管理员模式

当前执行的所有命令都具有管理员权限
```

对于：

```text
destructive
```

命令进一步提高视觉警示。

# 37. Working Directory Safety

还有一个容易忽略的问题。

例如正在删除：

```text
D:\Project
```

但 Working Directory 是：

```text
D:\Project\build
```

Windows `rmdir` 不能删除当前正在使用的目录。

所以 DeletePaths 执行前必须检查：

```text
cwd != target
```

并且：

```text
cwd 不在 target subtree 中
```

如果冲突：

```text
自动使用 CmdBox Temp Directory
```

或者拒绝执行。

Built-in Delete 默认：

```text

=

```

# 38. 环境变量

Runner 继承当前用户环境。

但：

```text
Execution History
```

绝不能保存全部 Environment。

因为环境变量里很可能有：

```text
TOKEN

```

```text
Command Block 显式配置的非 Secret Environment
```

# 39. Exit Code 不能简单判断 `!= 0 = 失败`

例如 Robocopy。

Microsoft 当前文档明确说明：

```text
0~7
```

都不代表复制失败；

```text
>= 8
```

才表示至少发生一次失败。

所以：

```rust
if exit_code == 0 {
    Success
} else {
    Failed
}
```

这个设计必须删除。

# 40. 增加 Outcome Policy

Command Block 增加：

```rust
struct OutcomePolicy {
    success: ExitCodeMatcher,

    warning: Option<ExitCodeMatcher>,
}
```

例如普通命令：

```text
Success
0

Failure
其它
```

Robocopy：

```text
Success
0~1

Completed With Warnings
2~7

Failure
>=8
```

这样 UI 可以显示：

```text
✓ 执行成功
```

或者：

```text
⚠ 执行完成，但存在差异
```

而不是错误地显示红色 Failure。

# 41. Execution State 和 Outcome 分离

因此下一版 State Machine 不应该再只有：

```text
succeeded
failed
cancelled
```

应该分成两个概念。

### Lifecycle

```text
PREPARING
STARTING
RUNNING
CANCELLING
FINISHED
INTERRUPTED
```

### Outcome

```text
SUCCESS
WARNING
FAILURE
NONE
```

例如：

```text
FINISHED
+
WARNING
+
exitCode = 3
```

就是合法状态。

这会在下一步 State Machine 中正式冻结。

# 42. Hero Delete 不能继续使用 `ErrorAction Continue`

你最开始那段：

```powershell
Remove-Item ... -ErrorAction Continue
```

对于人工 Terminal 使用没问题。

但是作为 CmdBox Built-in，不够可靠。

因为某一个目录失败：

```text
Access Denied
```

脚本仍然可能继续，并最终导致进程状态无法准确反映“有删除失败”。

Built-in Template 应改成：

```powershell
$failed = 0

foreach ($path in ...) {
    try {
        Write-Host "正在删除：$path"

        Remove-Item `
            -LiteralPath $path `
            -Recurse `
            -Force `
            -ErrorAction Stop
    }
    catch {
        $failed++
        Write-Error "删除失败：$path"
        Write-Error $_
    }
}

if ($failed -gt 0) {
    exit 1
}

exit 0
```

这样：

```text
5 个成功
1 个失败
```

至少不会显示：

```text
✓ 全部成功
```

---

# 43. Built-in 必须使用 Literal Path

PowerShell `-Path` 支持 wildcard，而 `-LiteralPath` 表示按字面值处理路径。

所以：

```text
File
Folder
Files
Folders
```

这种 Typed Path 在 Built-in PowerShell Command 中默认使用：

```powershell
-LiteralPath
```

避免：

```text
[
]
*
?
```

这种路径字符被解释成 Pattern。

# 44. Process 成功与 CmdBox 保存失败必须分开

例如：

```text
Command
✓ 成功

SQLite
✗ Disk Full
```

不能给用户显示：

```text
命令执行失败
```

因为命令实际上已经执行成功。

所以 Execution 至少需要区分：

```text

```

和：

```text
Persistence Health
```

例如：

```text
✓ 命令执行成功

⚠ 执行历史保存失败
```

这对删除命令尤其重要。

否则用户可能以为：

> 删除没执行。

然后再执行一遍。

至少做到：

```text

Current-user access
Write complete
Flush
Hash
Verify before spawn
```

# 53. 当前约束与后续目标

| 范围 | `CMD-02` 当前约束 |
|---|---|
| Runner | 只接受 `windowsPowerShell` / `cmd`，并解析确定系统位置 |
| Exit Code | `Finished` 保留原始 Exit Code，不推断业务 Outcome |
| 当前安全 | 两条 normal Echo 返回 Safety notApplicable；没有破坏性路径执行 |
| Preview | 绑定完整 ExecutionSpec |
| Path | Folder/Folders 只做当前 Definition 要求的根对象校验和回显，不建立生产 Path Fingerprint |
| Windows Spawn | Suspended → Job → Resume |
| PowerShell 临时脚本 | Windows PowerShell 使用 UTF-8 BOM |
| Command 编辑 | 默认 Built-in 来自只读 Rust Registry；当前没有复制、编辑或删除入口 |
| 执行结果 | 只表达 Lifecycle、原始 Exit Code、耗时和有界 Output |

后续破坏性与持久化单元必须继续满足：

| 范围 | 后续必须达到的设计约束 |
|---|---|
| Outcome | 由 Command-specific Outcome Policy 解释，且与 Lifecycle 分离 |
| 破坏性安全 | Structured SafetyPolicy 在 Preview/Run 两次执行 |
| 路径身份 | Final Path + Reparse Check + Path Fingerprint，并进入新版 Execution Spec |
| Command 管理 | Built-in 保持只读；复制后才能形成可编辑 User Command |
| 永久删除结果 | 使用明确的目标级错误聚合、Exit Code 与 Outcome，不从 stdout 猜测 |

---

# 54. 安全原则冻结

从这一版开始，建议把以下原则视为 CmdBox 不轻易突破的架构约束：

> **第一，前端永远不能直接执行任意系统进程。**

> **第二，用户看到的 Preview 必须绑定到完整 ExecutionSpec。**

> **第三，Destructive Command 必须在 Run 时重新验证目标。**

> **第四，文件夹安全检查不能通过递归扫描换取安全感。**

> **第五，Cancel 必须针对整个 Process Tree。**

> **第六，CmdBox Core 退出后，其 Execution 不能继续失控运行。**

> **第七，外部命令的成功与否由 Command 的 Outcome Policy 判断，而不是假设 Exit Code 只能是 0。**

> **第八，日志、数据库、UI 的错误不能改变已经发生的 Command Outcome。**

---

# 55. 风险覆盖与证据边界

本设计覆盖的核心风险包括：误选磁盘根目录或系统目录、路径特殊字符、目标身份变化、Command Block 修改、重复点击、PowerShell Profile 污染、Execution Policy 差异、中文与长路径、进程树逃逸、日志或数据库故障以及不可信输出。

`CMD-02` 已实现并在真实 Windows/Tauri 宿主验证的是双 Runner normal Echo、完整 Hash 复验、进程树、Output 与 Cancel；其余破坏性路径、Outcome、持久化和编辑能力仍是后续设计。任何后续能力只有取得对应自动与真实宿主证据后，才能从设计要求改写为已实现。
