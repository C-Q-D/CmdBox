# CmdBox 技术设计 v0.1

## 1. 本阶段技术目标

CmdBox v0.1 只解决一种执行模型：

> **一次性本地命令执行**

生命周期：

```text
Command Block
     ↓
输入参数
     ↓
参数校验
     ↓
渲染脚本
     ↓
安全检查
     ↓
启动本地进程
     ↓
实时 stdout / stderr
     ↓
进程结束
     ↓
记录执行历史
```

暂不支持：

- Interactive Shell
- SSH Session
- stdin 交互
- PTY
- REPL
- Workflow
- Remote Runner

# 3. 最重要的架构原则

前端不能直接获得“执行任意 Shell”的能力。

不采用：

```text
React
  ↓
execute("任意字符串")
  ↓
Shell
```

采用：

```text
React
  ↓
run_command_block(blockId, parameters)
  ↓
Rust Core
  ↓
Validate
  ↓
Render
  ↓
Safety Guard
  ↓
Process Manager
  ↓
OS
```

也就是说：

> React 只负责表达“用户想运行哪个 Command Block，以及填写了哪些参数”。

最终实际运行什么，由 Rust 决定。

---

# 4. Command Block

Command Block 是整个产品最核心的数据结构。

一个 Command Block 表示：

> 一个可以通过参数配置并重复执行的操作。

例如：

```text
快速删除文件夹
```

它不是保存：

```text
某一次具体删除命令
```

而是保存：

```text
操作模板
+
参数定义
+
Runner
+
安全属性
```

---

# 5. Command Block Schema v1

建议 JSON 模型如下：

```json
{
  "schemaVersion": 1,

  "id": "0198xxxx",

  "name": "快速删除多个文件夹",
  "description": "使用 PowerShell 永久删除一个或多个文件夹",

  "categoryId": "windows-files",
  "tags": ["windows", "delete", "folder"],

  "favorite": true,

  "runner": {
    "type": "powershell"
  },

  "template": "$ErrorActionPreference = 'Continue'\n\n{{#each paths}}\nWrite-Host \"正在删除：\" {{this}}\nRemove-Item -LiteralPath {{this}} -Recurse -Force -ErrorAction Continue\n{{/each}}",

  "parameters": [
    {
      "key": "paths",
      "label": "要删除的文件夹",
      "description": "支持一次选择多个文件夹",
      "type": "folders",
      "required": true,
      "remember": false,
      "constraints": {
        "minItems": 1,
        "mustExist": true
      }
    }
  ],

  "workingDirectory": {
    "mode": "default"
  },

  "environment": [],

  "execution": {
    "timeoutSeconds": null,
    "allowCancel": true
  },

  "safety": {
    "level": "destructive",
    "actionLabel": "永久删除"
  },

  "createdAt": "2026-08-22T10:00:00Z",
  "updatedAt": "2026-08-22T10:00:00Z"
```

# 6. Runner

第一版定义：

```ts
type RunnerType =
  | "powershell"
  | "cmd"
  | "bash"
  | "zsh";
```

但实现阶段：

```text
M1
├─ PowerShell
└─ CMD

M2
├─ Bash
└─ Zsh
```

用户不能在 MVP 里随便填写：

```text
runnerExecutable = C:\xxx\xxx.exe
```

Runner 必须由 CmdBox 自己解析。

例如：

```text
powershell
    ↓
优先 pwsh
    ↓
不存在
    ↓
Windows PowerShell
```

这样后续可以统一处理：

- 参数
- Encoding
- Environment
- Process Tree
- Cancel
- Exit Code

# 7. 参数类型

MVP 定义以下类型：

```ts
type ParameterType =
  | "text"
  | "number"
  | "boolean"
  | "select"
  | "file"
  | "folder"
  | "files"
  | "folders";
```

其中对 CmdBox 很重要的是：

```text
folder
folders
file
files
```

这些不是普通 Text。

它们对应原生 File Picker。

# 8. ParameterDefinition

```ts
interface ParameterDefinition {
  key: string;

  label: string;

  description?: string;

  type: ParameterType;

  required: boolean;

  defaultValue?: unknown;

  remember?: boolean;

  constraints?: {
    min?: number;
    max?: number;

    minItems?: number;
    maxItems?: number;

    mustExist?: boolean;
  };

  options?: Array<{
    label: string;
    value: string;
  }>;
}
```

例如 Robocopy：

```json
{
  "key": "threads",
  "label": "线程数",
  "type": "number",
  "required": true,
  "defaultValue": 32,
  "constraints": {
    "min": 1,
    "max": 128
  }
}
```

---

# 9. Parameter Value 和 Parameter Definition 分离

这是一个重要设计。

Command Block 保存：

```text
这个参数是什么
```

不保存：

```text
用户这一次输入了什么
```

例如：

```text
Parameter Definition

host
类型：text
默认值：null
```

实际执行时：

```text
Execution Input

host = 192.168.1.100
```

两者不能混在一起。

---

# 10. “记住上一次输入”单独保存

例如：

```text
Robocopy 高速复制
```

用户上一次输入：

```text
source = D:\Project
target = E:\Backup
threads = 32
```

下一次可以自动填充。

但这些数据不写回：

```text
CommandBlock.parameters
```

而是单独保存：

```text
command_parameter_state
```

逻辑：

```text
Command Definition
        │
        ├── Default Value
        │
        └── Runtime Last Value
```

这样不会污染 Command Block 本身。

# 11. Template Engine

第一版不使用复杂模板语言。

只支持非常有限的语法。

## 11.1 Scalar

```text
{{source}}
```

## 11.2 Boolean Condition

```text
{{#if noProgress}}
/NP
{{/if}}
```

## 11.3 Array Loop

```text
{{#each paths}}

...

{{this}}

{{/each}}
```

除此之外暂时不支持：

- JavaScript 表达式
- Function
- Eval
- Arithmetic
- Shell Expression
- 用户定义 Helper
- 任意代码执行

模板系统越简单，越容易保证行为确定。

---

# 12. 参数不能直接字符串 replace

禁止这样实现：

```ts
template.replace("{{path}}", path)
```

因为用户参数可能是：

```text
D:\My Files\Test
```

甚至包含：

```text
'
"
&
$
(
)
;
```

因此：

```text
参数值
↓
Parameter Serializer
↓
Shell-specific Literal
```

---

# 13. Shell Serializer

不同 Runner 有不同序列化器：

```text
PowerShellSerializer
CmdSerializer
BashSerializer
ZshSerializer
```

例如用户实际选择：

```text
D:\My Project\Test
```

PowerShell 渲染成合法字符串 literal：

```powershell
'D:\My Project\Test'
```

CMD：

```cmd
"D:\My Project\Test"
```

Bash：

```bash
'D:\My Project\Test'
```

因此模板作者只写：

```powershell
Remove-Item -LiteralPath {{path}} -Recurse -Force
```

而不是：

```powershell
Remove-Item -LiteralPath "{{path}}" -Recurse -Force
```

**模板中的参数是否需要引号，不应该由用户考虑。**

---

# 14. Number 参数

Number 经过严格校验以后，可以直接输出：

```text
32
```

例如：

```text
/MT:{{threads}}
```

最终：

```cmd
/MT:32
```

用户如果输入：

```text
32 & something
```

会在 Number Validator 阶段直接失败。

不会进入 Template Engine。

---

# 15. Boolean 参数

Boolean 不直接输出：

```text
true
false
```

推荐用条件语法。

例如：

```text
{{#if noProgress}}
/NP
{{/if}}
```

用户：

```text
☑ 不显示文件进度
```

最终：

```text
/NP
```

关闭时：

```text
''
```

即什么都不生成。

---

# 16. Array 参数

这是 CmdBox 第一版必须重点做好的地方。

例如：

```text
paths = [
  E:\release1,
  E:\release2,
  E:\release3
]
```

模板：

```powershell
{{#each paths}}

Write-Host "正在删除：" {{this}}

Remove-Item `
  -LiteralPath {{this}} `
  -Recurse `
  -Force `
  -ErrorAction Continue

{{/each}}
```

渲染结果：

```powershell
Write-Host "正在删除：" 'E:\release1'

Remove-Item `
  -LiteralPath 'E:\release1' `
  -Recurse `
  -Force `
  -ErrorAction Continue


Write-Host "正在删除：" 'E:\release2'

Remove-Item `
  -LiteralPath 'E:\release2' `
  -Recurse `
  -Force `
  -ErrorAction Continue
```

这比让用户自己维护：

```powershell
@(...)
```

简单很多。

---

# 17. 不支持 Raw Parameter

第一版明确不提供：

```text
{{parameter|raw}}
```

原因：

一旦存在 Raw：

```text
User Input
↓
不做 escaping
↓
直接进入 Shell
```

整个参数安全模型都会被绕过。

如果用户确实需要固定 Shell Flag：

直接写在 Template 里面。

例如：

```text
/E /MT:32 /NP
```

而不是把：

```text
/NP
```

作为用户自由输入内容。

---

# 18. Command Preview

点击执行前，Rust 负责：

```text
validate
↓
render
↓
返回 preview
```

前端调用：

```text
preview_command_block
```

获得：

```json
{
  "runner": "powershell",
  "script": "Remove-Item ...",
  "riskLevel": "destructive"
}
```

UI 显示：

```text
命令预览

────────────────────────

Remove-Item
  -LiteralPath 'D:\Test'
  -Recurse
  -Force

────────────────────────
```

因此 Preview 和真正执行的内容必须来源于**同一个 Renderer**。

不能：

```text
Frontend 自己生成 Preview
Backend 重新生成 Execution
```

否则有可能出现：

> 用户看到的不是实际执行的。

---

# 19. 一个关键决定：执行 Script File，而不是拼超长 `-Command`

Command Block 渲染完成后：

```text
Template
↓
Rendered Script
```

Rust 不直接拼：

```text
powershell.exe -Command "一大坨字符串..."
```

而是生成一个临时 Script：

```text
CmdBox Temp
└─ execution-0198xxxx.ps1
```

然后执行：

```text
PowerShell
↓
execution-0198xxxx.ps1
```

CMD：

```text
execution-0198xxxx.cmd
```

Bash：

```text
execution-0198xxxx.sh
```

---

# 20. 为什么采用临时 Script

这样可以避免很多问题：

### Command Line 长度

大量文件夹参数可能生成非常长的命令。

Script File 不受同样的命令行拼接限制影响。

### Quote 嵌套

避免：

```text
Rust String
↓
Windows CommandLine
↓
PowerShell -Command String
↓
Shell String
```

多层转义。

### Debug

Preview 内容和 Script 内容可以做到一致。

### Multi-line

天然支持：

```powershell
foreach (...)
{
   ...
}
```

而不是强迫所有命令压缩成单行。

---

# 21. 临时 Script 生命周期

```text
Render
↓
Create Temp Script
↓
Spawn Process
↓
Running
↓
Process Exit
↓
Delete Temp Script
```

临时脚本不长期保存。

执行历史只保存：

```text
Redacted Preview
```

而不是永久保留临时 `.ps1`。

# 23. RunCommandRequest

```rust
struct RunCommandRequest {
    command_block_id: String,

    parameters: HashMap<String, serde_json::Value>,
}
```

React 发送：

```json
{

  "parameters": {
    "paths": [
      "E:\\release1",
      "E:\\release2"
    ]
  }
}
```

注意：

**React 不发送最终命令。**

```json
{
```

```text

```

# 24. Run 生命周期

后端完整流程：

```text
1. Receive Request
        ↓
2. Load Command Block
        ↓
3. Validate Schema
        ↓
4. Validate Parameter Values
        ↓
5. Normalize Paths
        ↓
6. Safety Check
        ↓
7. Render Script
        ↓
8. Create Execution Record
        ↓
9. Create Temp Script
        ↓
10. Spawn Process
        ↓
11. Stream stdout/stderr
        ↓
12. Process Exit
        ↓
13. Finalize Execution
        ↓
14. Delete Temp Script
```

# 25. Execution ID

每一次执行都有独立：

```text
Execution ID
```

例如：

```text
0198f122-...
```

前端永远使用：

```text
executionId
```

控制任务。

不使用：

```text
PID
```

PID 是 Process Manager 内部实现细节。

# 26. Execution 状态

定义：

```ts
type ExecutionStatus =
  | "running"
  | "succeeded"
  | "failed"
  | "cancelled"
  | "interrupted";
```

正常：

```text
running
↓
succeeded
```

Exit Code 非 0：

```text
running
↓
failed
```

用户点击终止：

```text
running
↓
cancelled
```

CmdBox 崩溃或者电脑异常退出：

```text
running
↓
interrupted
```

应用下次启动时：

```text
所有遗留 running
↓
标记 interrupted
```

# 28. 为什么需要 sequence

stdout 和 stderr 是两个独立 Stream。

因此给所有事件生成：

```text

```

UI 就可以按照 CmdBox 收到事件的顺序展示。

例如：

```text

23 stderr
24 stdout
```

# 31. Cancel 的单位必须是“整个执行任务”

例如：

```text
CmdBox
  ↓
cmd.exe
  ↓
robocopy.exe
```

用户点击：

```text
终止任务
```

不能只保证：

```text
cmd.exe 被终止
```

而要保证整个：

```text
Execution Process Tree
```

被终止。

因此：

### Windows

Process Manager 使用：

```text
Job Object
```

把此次 Execution 的进程树作为一个单位管理。

### macOS / Linux

后续使用：

```text
Process Group
```

这属于 Execution Engine 的底层能力，不暴露到 React。

---

# 32. stdout / stderr

启动 Process 时：

```text
stdin  → Null
stdout → Pipe
stderr → Pipe
```

因为 MVP：

> 不支持 Interactive Input。

所以：

```text
stdin
```

根本不开放。

这可以进一步保证产品边界不会逐渐变成 Terminal。

---

# 33. Output 不全部放进内存

不能：

```text
一个 Robocopy 输出 500MB
↓
全部放 Zustand
```

同样也不应该：

```text
500MB stdout
↓
SQLite TEXT
```

推荐：

```text
Process
   │
   ├── Stream → React
   │
   └── Stream → Log File
```

例如：

```text
AppData/CmdBox/executions/
    0198xxx.log
```

SQLite 只保存：

```text
log_path
```

---

# 34. 前端 Output Buffer

运行时 React 只维护一个有限窗口。

例如：

```text
最近 5MB
```

超过后：

```text
丢弃最老的 UI Buffer
```

但是完整内容仍然保存在：

```text
Execution Log
```

因此不会因为命令疯狂输出导致整个 App 内存不断上涨。

# 36. 为什么需要 Snapshot

用户今天运行：

```text
快速删除
```

明天把 Command Block Template 改了。

历史记录仍应该告诉用户：

> 昨天实际运行的是什么。

所以执行时 Snapshot：

```text
Command Name
Parameters
Rendered Script
Runner
```

不能通过当前 Command Block 反推历史。

# 41. Safety Guard

执行之前统一经过：

```text
SafetyGuard
```

它负责的是：

> 降低误操作风险。

不是：

> 判断用户写的 Shell Script 是否绝对安全。

因为 Command Block 本身就是允许用户执行本地命令的。

# 42. Risk Level

第一版：

```ts
type RiskLevel =
  | "normal"
```

# 43. Path Safety

对于：

```text
file
folder
files
folders
```

Rust 可以进行额外路径安全检查。

例如删除类 Command Block：

```text
C:\
```

或者：

```text
D:\
```

这种磁盘根路径必须视为：

```text
Critical Target
```

同理 Unix：

```text
/
```

不能允许普通“一键执行”。

---

# 44. Safety Guard 不解析任意 Shell

第一版不要尝试做：

```text
AI / Parser
↓
分析一整段 PowerShell
↓
猜测它是否危险
```

这会迅速变成一个非常复杂的问题。

第一版安全模型主要依赖：

```text
Command Block riskLevel
+
Typed Parameters
+
Path Safety
+
用户可见 Preview
```

已经足够支撑 MVP。
