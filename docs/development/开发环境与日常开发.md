# CmdBox 开发环境与日常开发

本文是 CmdBox 开发环境、日常命令和高频启动策略的唯一权威说明。它只描述开发基础设施，不代表 `CMD-01` 或任何产品业务能力已经实现。

## 结论：日常不做完整重建

CmdBox 有两条开发路径，按本次修改需要选择：

| 场景 | 推荐入口 | 更新机制 | 何时需要重启 |
|---|---|---|---|
| 完整 Windows 桌面开发 | `dev.cmd` | React 使用 Vite HMR；Rust 使用 Tauri Watch + Cargo Incremental | Tauri 配置、依赖或开发进程异常时 |
| 纯前端界面开发 | `web-dev.cmd` | Compose Watch 同步文件；Vite HMR 更新页面 | Docker/Compose 配置或依赖清单变化时 |

完整桌面开发是最终验证主路径。Docker 只运行 React/Vite，不编译 Windows Tauri、不创建原生窗口，也不代替真实 PowerShell、CMD、WebView2 或 Windows API 验证。

## 首次检查

在仓库根目录运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check-env.ps1
```

检查项包括：

- Windows；
- Node.js 24 LTS 与 pnpm 11；
- Rust、Cargo、rustup 和 `x86_64-pc-windows-msvc` target；
- Visual Studio C++ Build Tools 与 x64 `cl.exe`；
- WebView2 Runtime；
- Docker CLI、Docker Compose 和 Docker Engine 状态；
- 本地 `127.0.0.1:7897` 包代理是否可用。

检查脚本不会安装系统软件，也不会修改用户级 npm/pnpm 配置。Docker Engine 停止时，普通检查只提示；严格检查可以使用：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check-env.ps1 -RequireDocker
```

当前工具链基线以 [Node.js 发布状态](https://nodejs.org/en/about/previous-releases)、[Tauri Windows 前置条件](https://v2.tauri.app/start/prerequisites/)和仓库 `package.json` 为准。

## 完整 Windows Tauri 开发

### 前台开发

```powershell
dev.cmd
```

适合人工开发：日志直接显示在当前终端，按 `Ctrl+C` 退出。脚本会先检查主机环境，再按依赖指纹决定是否运行 `pnpm install`，随后进入 `pnpm tauri dev`。

### 后台开发

```powershell
dev.cmd -Detached
```

适合 AI 验证或需要继续使用当前终端的场景。脚本只有在下面两项同时成立后才报告就绪：

1. `http://localhost:1420` 返回 CmdBox Vite 页面；
2. 当前仓库进程树中存在标题为 CmdBox 的真实原生窗口。

后台日志位于：

- `.cmdbox/tauri-dev.out.log`：Vite 标准输出；
- `.cmdbox/tauri-dev.err.log`：Tauri、Cargo Watch 与 Rust 编译输出；
- `.cmdbox/tauri-dev.json`：当前仓库后台 Worker 的受控状态。

### 停止与重启

```powershell
restart.cmd
stop.cmd
```

`restart.cmd` 只替换 `.cmdbox/tauri-dev.json` 记录且命令行归属当前仓库的进程树。`stop.cmd` 在停止前校验项目根目录和内部 Worker 路径，从叶进程到根进程清理 Vite、Cargo、Tauri CLI 与 `cmdbox.exe`，不会按进程名批量终止其他项目。

Tauri 与 Vite 的官方协作方式见 [Tauri 的 Vite 配置说明](https://v2.tauri.app/start/frontend/vite/)。日常前端修改由 HMR 处理，Rust 修改由 `tauri dev` 的文件监听处理。

## Docker 纯前端开发

### 前台开发

```powershell
web-dev.cmd
```

脚本会在需要时自动启动 Docker Desktop，然后运行 Compose Watch。按 `Ctrl+C` 后进入容器清理流程。

### 后台开发

```powershell
web-dev.cmd -Detached
web-stop.cmd
```

固定访问地址为 `http://localhost:1420`，Compose 服务名为 `frontend`。后台日志和状态位于：

- `.cmdbox/web-watch.out.log`；
- `.cmdbox/web-watch.err.log`；
- `.cmdbox/web-watch.json`。

容器不挂载 Docker Socket，也不挂载宿主 `node_modules`。镜像按 `package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml` 安装依赖；`src/` 修改只同步到容器并触发 HMR，依赖清单变化才触发重建。详细机制见 [Docker Compose Watch](https://docs.docker.com/compose/how-tos/file-watch/)。

## 依赖安装为什么不会每次重复

`scripts/ensure-deps.ps1` 共同计算以下文件的 SHA-256 指纹：

- `package.json`；
- `pnpm-lock.yaml`；
- `pnpm-workspace.yaml`。

当指纹与 `.cmdbox/dependencies.json` 一致且 `node_modules/.pnpm` 存在时，脚本直接跳过安装。只有依赖文件变化、模块目录缺失或显式传入 `-Force` 时，才运行：

```powershell
pnpm install --frozen-lockfile --prefer-offline
```

如果 `127.0.0.1:7897` 可用，HTTP 代理只设置在本次安装进程；脚本不会写 `.npmrc` 或用户级 pnpm 配置。依赖构建脚本默认拒绝，仓库只在 `pnpm-workspace.yaml` 中放行 Vite 构建链必需的 `esbuild`，符合 [pnpm Build Settings](https://pnpm.io/settings/build) 的显式允许模型。

## 高频开发命令

| 命令 | 用途 | 推荐时机 |
|---|---|---|
| `pnpm test:watch` | 只重跑受影响的前端测试 | 编写前端逻辑时持续运行 |
| `pnpm check:fast` | TypeScript 类型检查 + 前端单测 | 每个小改动完成后 |
| `pnpm build` | 类型检查 + Vite 生产构建 | 改动前端构建配置后 |
| `cargo check --manifest-path src-tauri/Cargo.toml` | 快速检查 Rust | 编写 Rust 时按需运行 |
| `pnpm check` | 前端完整检查 + Rust 格式与测试 | 每次提交前 |
| `pnpm tauri build` | 完整 Release Bundle | 里程碑和发布前，不用于日常重启 |

## 哪些修改需要什么动作

| 修改内容 | 需要的动作 |
|---|---|
| `src/**/*.tsx`、`src/**/*.ts`、CSS | 不重启；Vite HMR 自动更新 |
| `src-tauri/src/**/*.rs` | 不手工重启；Tauri Watch 自动增量编译并替换窗口进程 |
| `package.json` / pnpm 锁文件 | 主机下次 `dev.cmd` 自动刷新依赖；Docker Compose Watch 自动重建镜像 |
| `Cargo.toml` / `Cargo.lock` | Tauri Watch 会重新编译；依赖变化较大时允许等待 Cargo 完成一次缓存 |
| `vite.config.ts` | 主机 Vite 自动重载配置；Docker Watch 同步并重启前端服务 |
| `tauri.conf.json` / capabilities | 使用 `restart.cmd` 重新建立完整开发进程 |
| `compose.yaml` / `docker/Dockerfile.dev` / `.dockerignore` | `web-stop.cmd` 后重新运行 `web-dev.cmd` |
| 发布资源、Bundle 设置 | 只在发布门禁运行 `pnpm tauri build` |

## 本机实测参考

2026-08-22 在当前 Windows 主机与已填充缓存下取得以下结果；这些数字用于发现明显退化，不是跨机器硬性 SLA：

| 路径 | 本机结果 |
|---|---|
| `pnpm check:fast` | 约 5 秒，1 个前端渲染测试通过 |
| 依赖指纹未变化 | 约 0.32 秒，跳过 `pnpm install` |
| Docker 后台缓存启动 | 约 10–13 秒，HTTP 200 且容器 healthy |
| 完整 Tauri 后台缓存启动 | 约 9–13 秒，真实 CmdBox 窗口与 HTTP 同时就绪 |
| 前端修改 | Vite 日志确认 HMR，`cmdbox.exe` PID 不变 |
| Rust 注释修改 | Cargo 增量编译约 5 秒，Tauri 自动替换窗口进程 |
| 优化后完整后台重启 | 约 10.9 秒，旧 Worker 退出且新窗口就绪 |

## 常见问题

### 端口 1420 被占用

Docker 前端与 Windows Tauri Dev 共用固定端口，不能同时启动。先运行对应的 `web-stop.cmd` 或 `stop.cmd`，再进入另一条开发路径。

### Docker Engine 没有运行

`web-dev.cmd` 会尝试从默认安装路径以隐藏窗口启动 Docker Desktop并等待 Engine。若超时，打开 Docker Desktop 查看 WSL、虚拟化或登录错误，再运行严格环境检查。

### 后台启动失败

查看 `.cmdbox/*out.log` 与 `.cmdbox/*err.log`。启动脚本在超时或 Worker 提前退出时会调用精确停止入口，避免留下半启动进程。

### 依赖安装失败

先运行 `scripts/check-env.ps1`，再确认代理或直连网络。不要通过修改用户级 npm/pnpm 配置绕过本仓库规则；修复网络后运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ensure-deps.ps1 -Force
```

## 开发边界

当前环境只提供可构建、可测试、可热更新的空 CmdBox 骨架。没有新的明确授权时，不得根据本文入口自动进入 Command Block、命令执行、永久删除、SQLite 业务表或其他 `CMD-01` 产品实现。
